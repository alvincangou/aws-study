SAA-C03 : méthode & Well-Architected

Sécurité identité, privilège minimal, chiffrement (au repos et en transit), segmentation et traçabilité CloudTrail avant toute optimisation.
Résilience supprimer les SPOF, répartir sur plusieurs AZ, découpler et prévoir la restauration testée. Multi-AZ protège d’une panne d’AZ ; multi-Region protège d’une panne régionale.
Performance choisir selon le pattern d’accès, la latence, le débit, la taille et la cohérence ; préférer cache, asynchronisme et scale-out au surdimensionnement.
Coût comparer coût fixe/variable, trafic inter-AZ, stockage, licences et effort d’exploitation. « Managed/serverless » réduit souvent l’ops, mais pas toujours le coût unitaire.
Réflexe d’examen : relever le qualificatif principal (« least operational overhead », « lowest cost », « near-zero RTO »), les contraintes absolues (RTO, protocole, chiffrement, ordre, cohérence), puis éliminer les réponses qui violent une propriété native AWS.

IAM, sécurité & gouvernance

IAM Least privilege : une policy JSON combine Effect, Principal, Action, Resource, Condition. Préférer les rôles temporaires à des clés longues et limiter chaque identité à son besoin réel.
IAM Identity Center Fédération SSO centralisée vers plusieurs comptes ; connecter un IdP SAML 2.0/OIDC et éviter les utilisateurs IAM locaux dupliqués.
Organizations / SCP Une SCP ne donne jamais un droit : elle définit le plafond applicable à un compte/OU. Un explicit deny dans IAM, SCP ou permission boundary gagne toujours.
KMS Chiffrement d’enveloppe : une data key chiffre les données, la CMK chiffre la data key. La key policy doit autoriser explicitement les comptes/rôles externes.
CloudTrail Journaliser les appels API (management/data events selon le besoin), centraliser les logs dans S3 et protéger l’historique contre l’altération.
GuardDuty Détection managée de menaces via CloudTrail, VPC Flow Logs et DNS ; Inspector recherche les vulnérabilités EC2/ECR/Lambda ; Security Hub agrège les findings.
ABAC vs RBAC ABAC (Attribute-Based Access Control) utilise des tags dynamiques (aws:PrincipalTag/department == aws:ResourceTag/department) pour autoriser sans modifier les policies.
KMS vs CloudHSM KMS = managé multi-tenant FIPS 140-2 L2/L3 ; CloudHSM = boîtier dédié mono-tenant FIPS 140-2 L3 sous contrôle cryptographique direct du client (PKCS#11/JCE).
Hiérarchie de décision : refus implicite par défaut → allow explicite requis → tout explicit deny annule l’allow. IAM décide qui ; SCP/permission boundary limitent jusqu’où.

IAM avancé : les couches d’autorisation

Identity policy attachée à un user/group/role ; accorde un droit si l’action, la ressource et les conditions correspondent.
Resource policy attachée à S3, SQS, SNS, KMS ou Lambda ; utile pour l’accès cross-account, avec un Principal explicite.
Permission boundary plafond d’un principal IAM ; elle ne donne aucune autorisation par elle-même. Session policy réduit encore les permissions d’une session STS.
STS AssumeRole fournit des credentials temporaires ; vérifier trust policy du rôle, identity policy de l’appelant, durée et conditions ExternalId/MFA.
Access Analyzer détecte les accès externes involontaires et peut générer une policy à partir de l’activité CloudTrail.
Condition Keys aws:PrincipalOrgID (restreindre à l'OU/Org), aws:sourceVpce (forcer passage par Interface Endpoint), aws:RequestedRegion.
Piège IAM : une SCP, une permission boundary ou une key policy n’accorde pas automatiquement un droit. L’autorisation effective est l’intersection des couches applicables, avec priorité à l’explicit deny.

AWS Systems Manager (SSM) & Gestion de flotte

Session Manager connexion shell/SSH interactive sécurisée aux instances EC2 sans ouvrir le port 22 entrant, sans IP publique, sans bastion host et sans clés SSH ; audit complet dans CloudTrail et logs S3/CloudWatch.
Parameter Store hiérarchie clé-valeur (config et secrets chiffrés KMS). Standard (gratuit, 10 000 paramètres, 4 Ko) vs Advanced (payant, 8 Ko, policies de notification/TTL).
Secrets Manager conçu pour les secrets avec rotation automatique intégrée (RDS, Redshift, DocumentDB) via fonctions Lambda natives et réplication multi-régions pour DR.
Patch Manager automatisation du patching OS via Patch Baselines, fenêtres de maintenance (Maintenance Windows) et rapports de conformité.
Run Command & State Manager exécution de scripts et application de configurations d’état sans SSH sur des parcs entiers d'instances EC2/on-prem.
Prérequis Session Manager : l'instance EC2 doit exécuter l'agent SSM, posséder le rôle IAM avec AmazonSSMManagedInstanceCore et joindre les endpoints SSM (via NAT GW/Internet ou VPC Interface Endpoints ssm, ssmmessages, ec2messages).

Cognito & Fédération Web / Mobile

Cognito User Pools (CUP) Authentification (AuthN) : annuaire d'utilisateurs managé, inscription/connexion, MFA, Hosted UI, support IdP sociaux (Google, Apple, Facebook) et fédération d'entreprise SAML/OIDC. Émet des tokens JWT (ID, Access, Refresh).
Cognito Identity Pools Autorisation (AuthZ) : échange les tokens d’authentification (CUP, Google, SAML, anonyme) contre des credentials AWS temporaires IAM pour accéder directement à S3, DynamoDB, etc.
Lambda Triggers personnalisation des flux d'authentification (Pre-sign-up, Post-confirmation, Pre-token-generation, Custom auth challenge).
Accès direct client Identity Pools génère un rôle IAM pour chaque utilisateur ; avec les variables de policy (${cognito-identity.amazonaws.com:sub}), l'utilisateur n'accède qu'à son dossier privé s3://bucket/users/${sub}/.
Règle d'or : User Pool = annuaire et gestion d'utilisateurs (tokens JWT) ; Identity Pool = échange de jetons contre de vraies clés d'accès temporaires AWS (STS IAM).

Sécurité avancée des workloads

AWS WAF règles L7 contre SQLi/XSS, rate-based rules et managed rule groups sur CloudFront, ALB ou API Gateway. Shield protège contre DDoS ; Shield Advanced ajoute visibilité et protections avancées.
Network Firewall inspection stateful/stateless au niveau VPC, souvent centralisée dans une inspection VPC via TGW. Prévoir routes aller/retour et symétrie.
Macie découvre et classe les données sensibles/PII dans S3 ; Detective analyse les relations et la cause d’un finding ; Security Hub agrège les contrôles et findings.
ACM certificats TLS publics renouvelés automatiquement ; certificats privés via Private CA. Pour CloudFront, le certificat doit être dans us-east-1.
S3 hardening Block Public Access, bucket policy minimale, Object Ownership Bucket owner enforced, versioning, Object Lock et VPC endpoint policy selon le besoin.
Responsabilités : AWS sécurise le cloud (infrastructure) ; le client sécurise ce qu’il met dans le cloud (identités, données, configuration, patchs selon le service).

Limites & métriques à mémoriser

Service Repère utile Conséquence architecture
S3 Objet jusqu’à 5 To ; multipart recommandé dès gros objets et obligatoire au-delà de 5 Go. Paralléliser les parts, reprendre un upload interrompu et contrôler les coûts de requêtes.
Lambda Invocation maximale 15 min ; concurrence, mémoire, taille package et ephemeral storage limités. Utiliser SQS/Step Functions ou ECS/Fargate pour les traitements longs.
EBS gp3 sépare capacité, IOPS et débit ; io2 vise IOPS/durabilité élevées ; volume attaché à une AZ. Snapshot, réplication ou architecture applicative pour changer d’AZ.
DynamoDB Partition key bien distribuée ; capacité provisioned/on-demand, hot partitions et limites d’index à surveiller. Modéliser d’abord les accès ; ne pas traiter DynamoDB comme une table SQL.
API/SQS Payloads, timeout, visibilité, rétention et débit varient selon le type d’API/queue. Paginer, découpler, utiliser DLQ et rendre les consumers idempotents.
Attention : les Service Quotas évoluent et certaines limites sont augmentables. Mémoriser le principe et vérifier la limite exacte dans la console lorsque la question la fournit.

VPC Core & connectivité

VPC Régionnel et isolé : subnets associés à une AZ, route tables et CIDR non chevauchants. Public signifie route vers Internet Gateway, pas seulement une IP publique.
Security Group Au niveau ENI, stateful, uniquement Allow : le retour d’une connexion autorisée est accepté automatiquement.
NACL Au niveau subnet, stateless, Allow et Deny ; règles évaluées par numéro croissant. Autoriser explicitement les ports éphémères de retour (1024–65535).
Endpoints Gateway Endpoint pour S3/DynamoDB (route table, pas de coût horaire) ; Interface Endpoint/PrivateLink pour la plupart des APIs, ENI privés et coût par AZ/données.
NAT Gateway Sortie Internet depuis privé, déployer par AZ pour résilience. Internet Gateway sert au public ; NAT Gateway n’autorise pas les connexions entrantes. Egress-Only IGW assure la sortie IPv6 uniquement (gratuit, stateful).
Peering / TGW Peering est direct, privé et non transitif ; Transit Gateway devient le routeur régional hub-and-spoke pour de nombreux VPC et VPN.
Direct Connect Liaison dédiée et stable, mais pas chiffrée par défaut : ajouter VPN/IPsec si le chiffrement est requis. Public VIF pour services publics, private VIF pour VPC, transit VIF vers DXGW/TGW.
Hybride & Diagnostic DHCP Option Sets permet de configurer des serveurs DNS custom (AD on-prem) ; Traffic Mirroring clone le trafic ENI vers des appliances IDS hors-bande.
Piège Examen : un Security Group ne peut pas refuser une IP ; utiliser un NACL, AWS WAF ou une policy adaptée. Un VPC endpoint évite NAT/Internet uniquement pour les services qu’il dessert.

Edge & Accélération : CloudFront vs Global Accelerator

Global Accelerator fournit 2 adresses IP Anycast statiques mondiales ; route le trafic au niveau L4 (TCP/UDP) directement sur le réseau dorsal AWS vers le point de présence le plus proche. Idéal pour protocoles non-HTTP (VoIP, jeux, IoT, raw TCP/UDP) et failover multi-régions quasi instantané (< 1 min via health checks).
CloudFront CDN global au niveau L7 (HTTP/HTTPS) : met en cache le contenu statique et dynamique sur 600+ Edge Locations ; TLS termination ACM (us-east-1), signed URLs/cookies, Origin Access Control (OAC) vers S3, WAF/Shield.
Fonctionnalité CloudFront Functions Lambda@Edge
Runtime / Langages JavaScript (sub-millisecond) Node.js ou Python
Exécution 215+ Edge Locations (avant cache) Regional Edge Caches (13+)
Temps max & Mémoire < 1 ms / 2 Mo Jusqu'à 5s (viewer) ou 30s (origin) / 10 Go
Accès réseau & Body Aucun accès réseau / Pas d'accès au body Accès réseau externe, DB et inspection du body
Cas d'usage typique Réécriture d'URL, redirection, manipulation de headers Auth complexe, resize d'images à la volée, SSR, appels API
Distinction Examen : Protocole non-HTTP (TCP/UDP) ou IP Anycast statique requise → Global Accelerator. Caching web HTTP/S, protection WAF ou vidéo HLS/DASH → CloudFront.

S3, EBS & systèmes de fichiers

S3 Objet durable, multi-AZ par conception, clé unique par bucket. Versioning protège des suppressions ; Object Lock/WORM impose rétention et legal hold ; SSE-S3 par défaut, SSE-KMS pour contrôle/audit de clés.
S3 classes Standard (actif), Intelligent-Tiering (accès imprévisible), Standard-IA/One Zone-IA (moins fréquent), Glacier Instant/Flexible/Deep Archive (archives). Lifecycle automatise transitions et expiration.
S3 performance Multipart upload pour objets volumineux, presigned URL pour accès temporaire, Transfer Acceleration pour longue distance, CloudFront pour cache global. S3 fournit une forte cohérence read-after-write sur les opérations d’objets ; gérer tout de même retries, erreurs et conflits de réplication.
EBS Bloc attaché à une AZ : gp3 (SSD général, IOPS/throughput séparables), io2 Block Express (IOPS et durabilité critiques), st1 (throughput séquentiel), sc1 (cold). Snapshots incrémentaux S3, chiffrables KMS.
EFS NFS élastique partagé, multi-AZ et adapté à plusieurs EC2/Lambda ; EFS IA réduit le coût des fichiers peu consultés.
FSx Windows File Server pour SMB/AD, Lustre pour HPC/ML et throughput élevé, NetApp ONTAP pour fonctions enterprise, OpenZFS pour workloads ZFS.
Repères : EBS = bloc et une AZ ; EFS = fichiers POSIX partagé ; S3 = objets et API HTTP ; FSx = protocole/plateforme spécialisée. Ne pas monter un volume EBS normal simultanément sur plusieurs AZ.

EC2, Auto Scaling & Placement

EC2 Choisir une famille selon CPU, mémoire, réseau, stockage local ou accélérateur. User data automatise le bootstrap ; AMI et Launch Template rendent le déploiement reproductible.
On-Demand Flexibilité sans engagement ; Reserved/Savings Plans remise contre engagement ; Spot capacité interruptible avec risque de récupération : batch, workers et workloads tolérants.
ASG (Auto Scaling Group) un groupe d’instances décrit par un Launch Template avec une capacité min / desired / max, répartie sur plusieurs AZ pour éliminer le SPOF. Un health check (EC2 ou ELB) déclenche le remplacement automatique des instances « unhealthy » ; l’ASG s’attache à un ELB qui route le trafic vers les instances passées en service.
Élément ASG Rôle clé
Launch Template AMI, type d’instance, user data, EBS, security group ; recommandé car versionné et reproductible.
min / desired / max Bornent la capacité ; desired est la cible initiale, ignorée si elle sort des bornes.
Multi-AZ Instances réparties entre AZ ; une panne d’AZ ne bloque pas le service.
Health checks EC2 / ELB Remplacement automatique des instances « unhealthy ».
Scaling policies Pilotent la capacité au-delà du remplacement sur santé ; types et arbitrages détaillés dans le tableau ci-dessous.
Lifecycle hooks / Instance protection Pause avant launch/terminate (bootstrap, drain) ; protection contre les terminaisons involontaires.
Type de scaling Déclencheur Contexte idéal Limite clé
Manuel desired modifié à la main (console/CLI) Opération ponctuelle / maintenance Aucune réaction automatique ensuite
Simple 1 alarme CloudWatch, ajustement fixe (CPUUtilization > 70 % → +1) Charge homogène et tolérante Cooldown obligatoire, pas d’ajustement fin

Découpler avec SQS pour absorber les pics.
Réflexe : mesurer d’abord le pattern réel (CloudWatch), puis choisir : prévisible → scheduled/predictive ; réactif → target tracking par défaut ; précis par paliers → step ; ponctuel → manuel. Scheduled et predictive complètent, ils ne remplacent pas une réponse réactive.
Placement Groups contrôlent la disposition physique des instances sur le matériel AWS : Cluster = instances regroupées sur le même rack dans une seule AZ pour une latence ultra-basse et un throughput élevé ; Spread = instances sur du matériel totalement distinct pour une isolation maximale des pannes, mais avec une limite stricte de 7 instances par AZ ; Partition = instances réparties sur des segments logiques à racks indépendants (jusqu’à 7 partitions par AZ) pour combiner grand scale et tolérance aux pannes matérielles.

Piège Examen : une action scheduled est statique : elle applique une capacité à l’heure T sans constater la charge réelle, donc un pic imprévu n’est pas couvert ; remplacer une instance « unhealthy » maintient seulement la capacité prévue : ce n’est pas du scaling. « scale to zero, stateless, trafic irrégulier » pointe vers Lambda/API Gateway ou Fargate/serverless ; une instance Spot n’est jamais le seul composant d’une base ou d’un service critique sans reprise.

Conteneurs AWS : ECS, EKS & Fargate Deep Dive

AWS Fargate Moteur de calcul serverless pour conteneurs : alloue CPU et mémoire à la demande et supprime la gestion opérationnelle (provisioning, patching OS, scaling de clusters ou VMs). Fargate n'est pas un orchestrateur autonome : c'est la couche d'exécution (compute engine) qui s'enfiche directement dans Amazon ECS et Amazon EKS.
Amazon ECS (Compute Options) orchestrateur de conteneurs natif AWS, simple et intégré :
  • AWS Fargate : conteneurs serverless avec zéro gestion de serveurs sous-jacents.
  • Amazon EC2 Instances : machines virtuelles traditionnelles gérées par le client (Capacity Providers, Auto Scaling Groups, AMI et patchs OS).
  • External Instances (ECS Anywhere) : serveurs physiques locaux on-premises ou VMs externes rattachés au control plane central ECS.
Amazon EKS (Compute Options) service Kubernetes managé par AWS pour la portabilité et les écosystèmes open-source :
  • AWS Fargate : pods Kubernetes serverless isolés au niveau VM et gérés via des Fargate Profiles.
  • EKS Managed Node Groups : instances EC2 dont AWS automatise le provisioning, le cycle de vie et les mises à jour de sécurité des AMIs.
  • Self-Managed EC2 Nodes : instances EC2 configurées manuellement et jointes au cluster pour un contrôle bas niveau maximal.
  • Karpenter : autoscaler de nœuds open-source haute performance qui provisionne instantanément les types d'instances EC2 optimaux selon les besoins des pods en attente (bypasse les groupes ASG et le Cluster Autoscaler standard).
  • Hybride / Outposts / EKS Anywhere : exécution de pods Kubernetes sur matériel on-premises ou racks AWS Outposts.
ECS IAM Roles Task Role = permissions accordées au code applicatif du conteneur (S3, DynamoDB) ; Task Execution Role = permissions accordées à l'agent ECS (pull d'images ECR, envoi des logs CloudWatch, déchiffrement de secrets KMS/SSM).
ECS Networking mode awsvpc recommandé (chaque tâche reçoit sa propre ENI et Security Group dédié, obligatoire sur Fargate).
Piège Examen Conteneurs : Fargate = moteur de calcul (pas d'orchestration) ; ECS = simplicité native AWS ; EKS = standard Kubernetes & portabilité ; Karpenter = autoscaling de nœuds EKS dynamique direct sans ASG.

Serverless, AppSync & Stratégies de déploiement

AWS Lambda exécution événementielle sans serveur (15 min max, mémoire 128 Mo à 10 Go avec CPU proportionnel, stockage éphémère /tmp jusqu'à 10 Go). Dans un VPC : utilise Hyperplane ENI ; requiert un NAT Gateway pour joindre Internet/APIs externes sans VPC Endpoint. Provisioned Concurrency élimine les cold starts ; Reserved Concurrency limite la concurrence maximale pour protéger la base de données aval.
API Gateway & AppSync HTTP APIs (faible latence, économique, OIDC/JWT) vs REST APIs (WAF, validation, API Keys, usage plans, cache d'API) vs WebSocket APIs (bidirectionnel temps réel). AppSync = GraphQL managé avec subscriptions WebSocket temps réel et connecteurs DynamoDB/Lambda directs.

Bases de données & caches

RDS Multi-AZ haute disponibilité avec réplica standby synchrone et failover ; le standby n’est pas une cible de lecture. Read Replicas servent à scaler les lectures et peuvent être promues.
Aurora stockage distribué répliqué sur 3 AZ/6 copies, séparation compute/storage, réplicas Aurora et endpoints reader/writer. Aurora Global Database vise lecture distante et DR cross-Region. Serverless v2 ajuste instantanément les ACUs ; Backtrack rembobine la DB à la seconde près ; Fast Cloning clone en copy-on-write sans surcoût initial.
DynamoDB NoSQL clé-valeur/document, accès par partition key ; GSI/LSI pour patterns de requêtes, on-demand ou provisioned capacity, DAX pour cache en mémoire microseconde transparent, Global Tables pour multi-région, TTL pour expiration automatique sans WCU, et TransactWriteItems pour transactions ACID multi-tables.
ElastiCache Redis pour structures riches, réplication/failover et sessions ; Memcached pour cache simple horizontal. MemoryDB fournit un datastore Redis durable.
Redshift data warehouse analytique ; OpenSearch recherche/logs ; Neptune graph ; DocumentDB document compatible MongoDB ; Timestream séries temporelles.
Choix rapide : transactions relationnelles = RDS/Aurora ; clé-valeur à très grande échelle = DynamoDB ; recherche texte/logs = OpenSearch ; analytique colonne = Redshift ; cache = ElastiCache.

Kinesis Data Services & Streaming Suite

Kinesis Data Streams le streaming temps réel en mode pull : les données sont ingérées dans des shards (1 Mo/s d’écriture, 2 Mo/s de lecture par shard) et consommées par des applications custom (KCL, Lambda, Spark, Flink). L’ordre est garanti par shard grâce à la partition key. Rétention 24 h par défaut jusqu’à 365 jours, mode at-least-once (consommateurs idempotents). Redimensionnement par SplitShard / MergeShards et Enhanced Fan-Out (2 Mo/s dédiés par consommateur avec latence HTTP/2 < 70 ms).
Kinesis Data Firehose livraison managée near real-time en mode push : aucun code consommateur, un buffer (1 Mo à 128 Mo, 60 à 900 s) est vidé vers S3, Redshift (via S3 COPY), OpenSearch, Splunk ou un endpoint HTTP personnalisé. Supporte la transformation Lambda à la volée, la conversion de format (JSON vers Parquet / ORC) et le partitionnement dynamique S3.
Kinesis Data Analytics (Apache Flink) analyse en continu et temps réel des flux de streaming : exécution de requêtes SQL streamées ou applications Apache Flink managées (Java, Scala, Python) ; fenêtrage temporel (tumbling, sliding, session windows), détection d'anomalies ML et enrichissement des flux avant réémission vers S3, Firehose ou Data Streams.
Kinesis Video Streams ingestion, stockage sécurisé et diffusion de flux vidéo et audio en direct (caméras de sécurité, capteurs IoT, drones) ; supporte WebRTC pour des communications interactives bidirectionnelles à ultra-faible latence et s'intègre avec Amazon Rekognition Video pour l'analyse visuelle en temps réel.
Amazon MSK Apache Kafka managé (brokers multi-AZ, connecteurs Kafka Connect, MSK Serverless) pour les architectures nécessitant une compatibilité standard open-source Kafka sans administrer les clusters d'infrastructure.

Route 53, observabilité & résilience

X-Ray traces distribuées pour localiser latence et erreurs entre API, Lambda et services. CloudTrail = audit API ; Flow Logs = métadonnées réseau ; CloudWatch = fonctionnement.
Piège Examen : CloudFront est une couche cache/edge, pas un remplacement de Route 53. Route 53 health check + failover DNS ne garantit pas que les clients ignorent instantanément le TTL.

SAP-C02 : axes de décision

Complexité organisationnelle — 26% réduire le blast radius, déléguer proprement, isoler les workloads et appliquer une gouvernance centralisée (SCPs préventives, Config détectif).

Réflexe SAP : plusieurs réponses peuvent être techniquement possibles. Retenir celle qui respecte toutes les contraintes, minimise l’effort opérationnel et limite le domaine d’impact d’une erreur.

Landing zone & multi-comptes

Organizations Root → OUs → comptes. Séparer management, log archive, security tooling, network/shared services, workloads dev/test/prod pour réduire le blast radius et clarifier la facturation.
Control Tower Automatise la landing zone, Account Factory et guardrails. Preventive guardrails = SCP ; detective guardrails = AWS Config ; proactive = CloudFormation Hooks. Une SCP bloque mais n’accorde jamais un droit IAM.
IAM Identity Center SSO centralisé vers les comptes et permission sets. Pour machine-to-machine, utiliser STS AssumeRole et des credentials temporaires, jamais une access key partagée.
Audit central Organization CloudTrail vers un compte log archive S3 avec bucket policy restrictive, Object Lock et séparation des rôles. Config Aggregator consolide la conformité ; GuardDuty admin agrège les findings.
FinOps AWS Budgets, Cost Categories/Allocation Tags et Billing Conductor pour visibilité et showback/chargeback entre business units.
SAP Gotcha : ne pas placer toutes les workloads dans un compte unique « pour simplifier ». Le multi-compte isole les permissions, quotas, logs, facturation et pannes ; une SCP mal appliquée peut toutefois casser les opérations d’un OU entier. Les SCPs ne s'appliquent jamais au Management Account.

Landing zone : composants clés & automatisation

Management account conserver le minimum d’actions, activer MFA, ne pas y héberger de workload et protéger l’accès root.
Log Archive S3 central pour CloudTrail, Config et logs réseau ; bucket policy restrictive, Object Lock, versioning et accès d’écriture uniquement pour les services.
Security Tooling delegated administrators pour GuardDuty, Security Hub, Inspector, Macie et IAM Access Analyzer ; centraliser findings et automatiser leur traitement.
Network / Shared Services TGW, DNS Resolver, endpoints, inspection, Active Directory, CI/CD et services partagés dans des comptes dédiés.
StackSets / Service Catalog StackSets déploie automatiquement des templates d'infrastructure sur toute nouvelle création de compte dans une OU ; Service Catalog fournit des portfolios avec Launch Constraints (délégation de droits IAM de déploiement). License Manager applique des quotas de licences (vCPU/cores).
Politiques d'Organisation Tag Policies (standardisation des clés/valeurs), Backup Policies (sauvegardes obligatoires), AI Opt-Out.
SAP Gotcha : un guardrail préventif empêche l’action via SCP ; un guardrail détectif constate une dérive via Config. Un contrôle détectif ne bloque pas la création initiale.

Transit Gateway, DX & Cloud WAN

TGW Hub régional pour VPC attachments, VPN et Direct Connect. Utiliser plusieurs route tables TGW (prod/shared/inspection) pour segmentation ; propagation et associations sont distinctes.
RAM partager TGW, subnets ou autres ressources avec des comptes/OU sans créer de peering full mesh. Le partage ne contourne ni IAM ni routes.
DX Gateway relie des Direct Connect locations à VPC via transit/private VIF ; annoncer uniquement les préfixes nécessaires et respecter les limites BGP (100 routes max).
Direct Connect Resiliency & LAG Maximum Resiliency (2 liaisons sur 2 sites DX distincts) vs High Resiliency (2 liaisons sur 1 site) ; LAG agrège jusqu'à 4 liaisons physiques actives/actives (LACP). SiteLink connecte les sites on-prem via le réseau dorsal AWS.
BGP Communities & Chiffrement Communautés BGP AWS (7224:7100 Low, 7224:7200 Med, 7224:7300 High) et AS-Path Prepending pour influencer le retour. Pour le chiffrement DX : MACsec (au débit nominal 10G/100G) ou VPN IPsec sur DX.
Inspection VPC TGW route table → appliance VPC/GWLB → retour symétrique avec TGW Appliance Mode. Cloud WAN gère un réseau global par segments déclaratifs (Core Network Policy).
Pattern : on-prem → DX/VPN → DXGW/TGW → inspection segment (GWLB) → workload VPC. VPN fournit le backup de DX ; deux tunnels terminés sur des AZ différentes apportent la résilience.
SAP Gotcha : DX est privé mais pas chiffré par défaut. Pour IPsec sur DX, combiner une public VIF + VPN public, ou une transit VIF + VPN à IP privée selon le design.

Hybrid DNS & PrivateLink

Route 53 Resolver inbound permet au DNS on-prem de résoudre les zones privées AWS via endpoints ENI. Outbound transmet les requêtes AWS vers les resolvers on-prem avec forwarding rules partagées par RAM.
Resolver rules centraliser les règles dans un compte réseau et les partager avec RAM. Attention aux boucles de forwarding, à la résolution conditionnelle et aux security groups des endpoints.
Private Hosted Zone associer à plusieurs VPC (ou architecture centralisée selon le besoin). Une zone publique et privée de même nom ont des réponses différentes selon le point de résolution.
PrivateLink provider → NLB → endpoint service ; consumer → interface endpoint. Accès unidirectionnel au service, sans route réseau globale ni CIDR non chevauchant requis.
Overlapping CIDR éviter Peering/TGW IP routing. PrivateLink résout l’exposition service-to-service ; Private NAT peut traduire des flux bidirectionnels quand une vraie connectivité IP est nécessaire.
SAP Gotcha : PrivateLink n’est pas un transit VPC généraliste et ne fournit pas une résolution DNS « magique ». Publier le nom privé, configurer endpoint DNS et autoriser le SG/NLB.

Réseau entreprise : routage & inspection

TGW route tables séparer les associations et propagations : prod peut atteindre shared-services, mais pas nécessairement dev ; documenter les routes effectives et les blackholes.
Central egress private subnets → TGW → egress VPC → NAT Gateway/Network Firewall → IGW. Déployer NAT et endpoints dans plusieurs AZ et contrôler le retour.
Inspection GWLB ou AWS Network Firewall pour filtrage east-west/north-south. La symétrie de routage est indispensable pour une appliance stateful (activer Appliance Mode sur l'attachement TGW).
DX + VPN Direct Connect fournit le chemin primaire ; VPN Site-to-Site redondant fournit le backup. Deux tunnels et deux points de terminaison évitent un SPOF.
Cloud WAN privilégier pour une politique réseau globale par segments ; TGW reste le choix régional classique pour connecter VPC, VPN et DX.
SAP Gotcha : une route annoncée dans TGW ne garantit pas le chemin retour. Vérifier les tables de routes VPC, TGW, appliance, DX/VPN et les filtres BGP dans les deux directions.

KMS, conformité & cross-account

KMS key policy dans un compte sécurité : autoriser l’utilisation par le compte consommateur (Principal: arn:aws:iam::CompteB:root), puis la policy IAM du rôle consommateur doit aussi permettre l’action. Les deux portes sont nécessaires.
Multi-Region keys clés répliquées avec même key material/logical key ID pour déchiffrer localement des données répliquées sans appel réseau distant ; elles ne remplacent pas la stratégie de réplication ni les contrôles d’accès.
S3 replication SRR/CRR, versioning sur les deux buckets, IAM role de réplication, KMS grants/key policy cross-account et ownership/ACL adaptés. Re-encryption KMS nécessaire lors d’un changement de clé.
SCP vs key policy une SCP peut bloquer l’appel KMS même si key policy et IAM autorisent ; la policy KMS ne peut pas outrepasser une SCP.
Compliance Config conformance packs, Security Hub standards, Macie pour PII S3, Audit Manager pour preuves et CloudTrail Lake pour analyse des événements sur 7 ans.
SAP Gotcha : cocher « encryption enabled » ne suffit pas. Vérifier région de la clé, grants, key policy, rôle de réplication, destination cross-account et capacité à restaurer.

DR d’entreprise : RTO/RPO

RTO temps de remise en service ; RPO fenêtre de perte. Définir les objectifs par application et classer les dépendances (DNS, IAM, secrets, réseau, données, observabilité).

Résilience opérationnelle (DRS / FIS)

Elastic Disaster Recovery réplication continue au niveau bloc de serveurs on-prem ou EC2 vers une staging area légère et lancement de l’infrastructure de reprise à la demande ; RPO en secondes et RTO en minutes.
Resilience Hub évalue les objectifs de résilience d’une application, identifie les écarts et propose des recommandations ; il ne remplace pas les tests de failover.
AWS Backup Vault Lock impose une rétention immuable en mode compliance ; combiner copies cross-account/cross-Region et politiques Organizations.
FIS Fault Injection Service teste volontairement des défaillances (chaos engineering) ; limiter l’expérimentation par IAM, tags, Stop Conditions CloudWatch automatiques et fenêtres approuvées.
Runbook inclure quotas, IAM, secrets, certificats ACM, DNS/TTL, réplication, dépendances tierces, observabilité, validation métier et procédure de retour arrière.
SAP Gotcha : une architecture multi-AZ ne suffit pas si le déploiement, les quotas régionaux, les secrets ou les permissions de restauration restent dans une seule région.

CloudFormation d'Entreprise & IaC

CloudFormation StackSets déploie et met à jour des stacks de manière centralisée à travers plusieurs comptes et plusieurs régions AWS en une seule opération ; s'intègre nativement avec AWS Organizations pour auto-déployer automatiquement sur tout nouveau compte ajouté dans une OU.
Gestion du cycle de vie DeletionPolicy (Retain pour préserver S3/RDS lors de la suppression de stack, Snapshot pour créer un snapshot de sauvegarde, Delete) et UpdateReplacePolicy.
Stack Policies politiques JSON attachées aux stacks pour interdire explicitement les mises à jour accidentelles de ressources critiques (ex: interdire la modification d'un cluster RDS de production).
Custom Resources permet d'écrire des scripts d'extension personnalisés déclenchés par Lambda lors des opérations CRUD du stack (ex: provisionner un certificat tiers, initialiser une base de données).
Architecture modulaire Nested Stacks (sous-stacks réutilisables orchestrés par un template parent) vs Cross-Stack References (Export et Fn::ImportValue pour partager des identifiants d'infrastructures communes, comme les VPC IDs). Drift Detection identifie les modifications manuelles hors IaC.

Architecture event-driven & API

EventBridge bus central et règles par événement pour découpler domaines. Archive/replay et schema registry aident la gouvernance des contrats. Supporte événements AWS, SaaS (Salesforce) et custom.

SNS fan-out vers plusieurs consommateurs ; combiner SNS→SQS pour isoler les vitesses de traitement. Step Functions gère workflow et compensation (Saga). Standard vs Express.
ECS/EKS/Fargate choisir ECS pour simplicité AWS, EKS pour exigences Kubernetes/portabilité ; Fargate réduit les opérations mais n’est pas toujours le meilleur coût pour capacité stable.
Pattern de migration : API facade → strangler routing → nouveau service → EventBridge/SQS → réplication/CDC → observabilité. Déployer blue/green, canary et feature flags pour limiter le risque.
SAP Gotcha : un bus d’événements n’est pas une file de travail. Utiliser EventBridge pour router, SQS pour retenir jusqu’à consommation et Step Functions pour orchestrer plusieurs étapes.

Cas d’entreprise — décisions à haute valeur

Banque mondiale : séparation réglementaire et reprise

Contraintes

  • Comptes prod séparés par région/régulateur, journaux immuables (WORM 7 ans) et accès opérateur fédéré.
  • RPO de quelques minutes et RTO inférieur à 15-30 minutes pour les bases critiques.

Architecture

Control Tower → OUs réglementaires → Identity Center avec MFA ; CloudTrail/Config/GuardDuty/Security Hub centralisés vers Log Archive avec S3 Object Lock ; Aurora Global/DynamoDB Global Tables selon le modèle de données ; Route 53 ARC / Global Accelerator pour le failover.
SAP Gotcha : la réplication multi-région n’est pas une garantie de cohérence transactionnelle universelle. Choisir le datastore selon les writes, conflits et exigences ACID. Pour écritures multi-régions simultanées, DynamoDB Global Tables.
Groupe industriel : datacenter, CIDR chevauchants et modernisation

Contraintes

  • Plusieurs sites avec CIDR historiques identiques, liaison DX principale avec redondance maximale et VPN de secours.
  • Exposer progressivement des APIs migrées sans connecter les réseaux entiers.

Architecture

DX redondant (Maximum Resiliency) + VPN → DXGW/TGW pour les préfixes non conflictuels avec VPC d'inspection centrale (GWLB / Appliance Mode) ; PrivateLink (NLB + endpoint service) pour les services aux CIDR conflictuels ; MGN/DMS/SCT pour migrer ; ECS/Fargate + EventBridge/SQS pour moderniser.
SAP Gotcha : PrivateLink expose un service, il ne résout pas une dépendance qui exige une connectivité IP bidirectionnelle complète. Pour cette dernière, examiner Private NAT et la re-numérotation.
Retail global : trafic variable et coûts

Contraintes

  • Pics saisonniers (Black Friday 50x), catalogue mondial, recherche rapide, données client chiffrées et équipes autonomes.
  • Éviter le sur-provisionnement et isoler les coûts par domaine.

Architecture

CloudFront + WAF en edge → API Gateway/Lambda ou ECS Fargate → DynamoDB Global Tables avec DAX pour accès clé-valeur mondial ; SQS FIFO + Step Functions pour commandes ; Cost Allocation Tags/Budgets pour FinOps.
SAP Gotcha : ne pas choisir une base relationnelle uniquement parce que les données sont « importantes ». Le pattern d’accès, les transactions et la cohérence décident du service.
