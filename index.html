SAA-C03 : méthode & Well-Architected

Sécurité identité, privilège minimal, chiffrement (au repos et en transit), segmentation et traçabilité CloudTrail avant toute optimisation.
Résilience supprimer les SPOF, répartir sur plusieurs AZ, découpler et prévoir la restauration testée. Multi-AZ protège d’une panne d’AZ ; multi-Region protège d’une panne régionale.
Performance choisir selon le pattern d’accès, la latence, le débit, la taille et la cohérence ; préférer cache, asynchronisme et scale-out au surdimensionnement.
Coût comparer coût fixe/variable, trafic inter-AZ, stockage, licences et effort d’exploitation. « Managed/serverless » réduit souvent l’ops, mais pas toujours le coût unitaire.
Réflexe d’examen : relever le qualificatif principal (« least operational overhead », « lowest cost / moins cher », « near-zero RTO », « sans opérations », « HA », « latence »), extraire les contraintes absolues (RTO, protocole, chiffrement, ordre, cohérence), éliminer les réponses qui violent une propriété native AWS ou les distracteurs invalides, puis choisir le service managé qui satisfait exactement le besoin.

IAM & Gestion des Accès : Identité, Rôles & Fédération

IAM (Identity and Access Management) Least privilege : une policy JSON combine Effect, Principal, Action, Resource, Condition. Préférer les rôles temporaires à des clés longues et limiter chaque identité à son besoin réel.
Identity vs Resource policy Identity policy attachée à un user/group/role ; accorde un droit si l’action, la ressource et les conditions correspondent. Resource policy attachée directement à S3, SQS (Simple Queue Service), SNS (Simple Notification Service), KMS (Key Management Service) ou Lambda ; indispensable pour l’accès cross-account avec un Principal explicite sans devoir assumer de rôle.
Permission boundary & Session policy Permission boundary définit le plafond maximal d’un principal IAM (Identity and Access Management) ; elle ne donne aucune autorisation par elle-même. Session policy passée lors d'un appel STS réduit encore les permissions d’une session temporaire.
AWS STS AssumeRole fournit des credentials temporaires (AccessKeyId, SecretAccessKey, SessionToken) ; vérifier trust policy (AssumeRolePolicyDocument) du rôle cible, identity policy de l’appelant, durée (15 min à 12 h) et conditions ExternalId (protection contre le confused deputy) et MFA.
Access Analyzer & Condition Keys Access Analyzer détecte les accès externes involontaires et peut générer une policy à partir de l’activité CloudTrail. Condition Keys clés : aws:PrincipalOrgID (restreindre à l'OU/Org), aws:sourceVpce (forcer passage par Interface Endpoint), aws:RequestedRegion, aws:PrincipalArn.
ABAC vs RBAC ABAC (Attribute-Based Access Control) utilise des tags dynamiques (aws:PrincipalTag/department == aws:ResourceTag/department) pour autoriser automatiquement sans modifier les policies lors des arrivées/mouvements d'employés.
IAM Identity Center Fédération SSO centralisée vers plusieurs comptes AWS ; connecter un IdP SAML 2.0/OIDC d'entreprise (Active Directory, Okta, Entra ID) et assigner des Permission Sets. Évite les utilisateurs IAM locaux dupliqués.
Hiérarchie de décision : refus implicite par défaut → allow explicite requis → tout explicit deny dans IAM, SCP ou boundary annule l’allow. IAM décide qui ; SCP et permission boundary limitent jusqu’où.
Piège IAM : l’autorisation effective est l’intersection de toutes les couches applicables : identity policy ∩ resource policy ∩ SCP ∩ permission boundary ∩ session/key policy ; chaque couche doit autoriser l’action demandée pour qu’elle soit permise.

Amazon Cognito : Authentification Web & Mobile

Cognito User Pools (CUP) Authentification (AuthN) : annuaire d'utilisateurs managé, inscription/connexion, MFA, Hosted UI prête à l'emploi, support IdP sociaux (Google, Apple, Facebook) et fédération d'entreprise SAML/OIDC. Émet des tokens JWT (ID, Access, Refresh).
Cognito Identity Pools Autorisation (AuthZ) : échange les tokens d’authentification (CUP, Google, SAML, invité anonyme) contre des credentials AWS temporaires IAM (Identity and Access Management) (via STS) pour accéder directement à S3, DynamoDB, etc., sans backend serveur.
Lambda Triggers personnalisation des flux d'authentification (Pre-sign-up, Post-confirmation, Pre-token-generation pour enrichir les claims, Custom auth challenge).
Accès direct client Identity Pools génère un rôle IAM pour chaque utilisateur ; avec les variables de policy (${cognito-identity.amazonaws.com:sub}), l'utilisateur n'accède qu'à son dossier privé s3://bucket/users/${sub}/.
Règle d'or : User Pool = annuaire et gestion d'utilisateurs (tokens JWT) ; Identity Pool = échange de jetons contre de vraies clés d'accès temporaires AWS (STS IAM).

Sécurité des Données : KMS, CloudHSM, Secrets & Certificats

AWS KMS (Key Management Service) Chiffrement d’enveloppe : une data key chiffre les données, la CMK/KMS Key chiffre la data key. La key policy doit autoriser explicitement les comptes et rôles externes (KMS n'accorde aucun droit par défaut). Supporte les Multi-Region Keys (même key material et key ID logique pour répliquer sans déchiffrement distant).
KMS vs CloudHSM KMS : managé multi-tenant FIPS 140-2 L2/L3 sous contrôle AWS. CloudHSM : boîtier physique dédié mono-tenant FIPS 140-2 L3 sous contrôle cryptographique direct et exclusif du client (PKCS#11, JCE, non managé par AWS).
AWS Secrets Manager Conçu spécifiquement pour les secrets avec rotation automatique intégrée (RDS (Relational Database Service), Aurora, Redshift, DocumentDB) via fonctions Lambda natives sans coupure de service. Réplication multi-régions pour DR.
Parameter Store (SSM) Hiérarchie clé-valeur pour configurations et secrets chiffrés KMS. Standard : gratuit, max 10 000 paramètres, 4 Ko. Advanced : payant, 8 Ko, policies de notification EventBridge et TTL. Pas de rotation automatique out-of-the-box.
AWS Certificate Manager (ACM) Provisionne et renouvelle automatiquement les certificats TLS publics gratuits. Certificats privés via Private CA. Règle absolue : pour CloudFront, le certificat ACM doit impérativement être créé dans la région us-east-1.
Arbitrage Examen : Secret de base de données avec rotation automatique requise → Secrets Manager. Configuration applicative ou secret statique économique sans rotation → Parameter Store. Clé de chiffrement FIPS mono-tenant dédiée sous contrôle direct client → CloudHSM.

Sécurité Périmétrique, Réseau & Détection des Menaces

AWS WAF(Web Application Firewall) règles L7 contre SQLi/XSS, rate-based rules (anti-bruteforce) et managed rule groups sur CloudFront, ALB (Application Load Balancer) ou API Gateway.
AWS Shield Shield Standard : protection DDoS L3/L4 automatique gratuite sur CloudFront, Route 53 et ALB. Shield Advanced : protection L7 avancée, couverture financière contre les surcoûts d'autoscaling causés par l'attaque et assistance de l'équipe SRT 24/7.
Network Firewall inspection stateful/stateless au niveau réseau VPC (L3–L7, filtrage Suricata), souvent centralisée dans une inspection VPC via Transit Gateway. Prévoir routes aller/retour et symétrie.
Firewall Manager centralise et applique automatiquement des policies de sécurité (AWS WAF, Shield Advanced, Security Groups, Network Firewall) sur tout un Organizations : les déploie sur les nouveaux comptes et détecte les ressources non conformes.
Amazon GuardDuty détection managée d'intrusions et d'anomalies par ML via l'analyse continue des logs CloudTrail (management et data events S3), VPC Flow Logs, DNS et EKS audit logs. Sans aucun agent à installer.
Amazon Macie découvre, classe et protège les données sensibles et PII (numéros de carte, pièces d'identité) dans Amazon S3 via ML et expressions régulières.
Inspector & Detective Inspector : recherche automatique des vulnérabilités (CVE) et exposition réseau sur EC2, ECR (Elastic Container Registry) et Lambda. Detective : analyse de graphes pour enquêter sur la cause racine d'un finding de sécurité.
Security Hub console centrale agrégeant et normalisant les contrôles et findings de GuardDuty, Inspector, Macie et Firewall Manager selon les standards CIS AWS Foundations et PCI-DSS.
Responsabilités : AWS sécurise le cloud (infrastructure physique, hyperviseurs, datacenters) ; le client sécurise ce qu’il met dans le cloud (identités, données, configuration, chiffrement, patchs applicatifs).

Gouvernance Multi-Comptes : AWS Organizations, SCPs & AWS Config

Organizations & SCP Une SCP (Service Control Policy) ne donne jamais un droit : elle définit le plafond maximal d'autorisations applicable à un compte ou à une OU. Un explicit deny dans une SCP gagne toujours sur les droits IAM locaux. Les SCPs ne s'appliquent jamais au Management Account.
AWS Control Tower Automatise le déploiement d'une landing zone multi-comptes selon les meilleures pratiques. Fournit l'Account Factory et des guardrails : préventifs (SCPs qui bloquent), détectifs (AWS Config qui alerte) et proactifs (CloudFormation Hooks).
AWS Config évalue la conformité des ressources par rapport à des règles (Config Rules), suit l’historique des modifications de configuration et détecte la dérive (drift) ; peut corriger automatiquement (remediation via SSM Automation) et agréger plusieurs comptes/régions dans un Config Aggregator.
RAM (Resource Access Manager) permet de partager des ressources (subnets, Transit Gateway, Route 53 Resolver rules, licences) entre comptes d'une organisation sans dupliquer ni créer de peering full mesh.
Réflexe d’examen : « Interdire préventivement une action sur un ensemble de comptes (ex: interdire de désactiver CloudTrail ou d'utiliser certaines régions) » → SCP. « Détecter a posteriori qu'une ressource n'est pas conforme et suivre les changements de configuration » → AWS Config. « Partager un subnet ou une TGW avec d'autres comptes » → AWS RAM.

VPC Core, Routage & Connectivité Hybride

VPC Régionnel et isolé : subnets strictement associés à une seule AZ, route tables et CIDR non chevauchants. Public signifie route vers Internet Gateway (IGW), pas seulement une IP publique.
Security Group Au niveau ENI, stateful (le retour d’une connexion autorisée est accepté automatiquement), uniquement règles Allow. Référençable par ID de Security Group pour autoriser des tiers sans IP fixes.
Network ACL Au niveau subnet, stateless (le retour doit être explicitement autorisé dans les deux sens), Allow et Deny ; règles évaluées par numéro croissant. Autoriser explicitement la plage de ports éphémères de retour (1024–65535).
Endpoints Gateway Endpoint pour S3 et DynamoDB uniquement (modifie la route table du VPC, aucun coût horaire ni de trafic) ; Interface Endpoint (PrivateLink) pour la plupart des autres APIs AWS (crée des ENI privés avec IP locale dans le subnet, facturé à l'heure et au Go).
Passerelles de sortie NAT Gateway : sortie Internet depuis une zone privée, déployer 1 par AZ pour la résilience (pas de connexions entrantes). Egress-Only Internet Gateway : sortie IPv6 uniquement (gratuit, stateful). NAT instance : alternative legacy sur EC2 (SPOF sans ASG, désactiver source/destination check, non managée).
Peering / Transit Gateway VPC Peering est direct, privé et non transitif (A↔B et B↔C ne permet pas A↔C) ; Transit Gateway devient le routeur régional hub-and-spoke pour interconnecter des milliers de VPC et liaisons VPN/Direct Connect.
Direct Connect Liaison dédiée et stable, mais pas chiffrée par défaut : ajouter VPN/IPsec ou MACsec si le chiffrement est requis. Public Virtual Interface pour services publics (S3/DynamoDB), private Virtual Interface pour VPC, transit Virtual Interface vers Direct Connect Gateway/Transit Gateway.
Hybride & Diagnostic DHCP Option Sets permet de configurer des serveurs DNS custom (AD on-prem) ; VPC Flow Logs surveille les flux réseau ; Traffic Mirroring clone le trafic ENI vers des appliances IDS hors-bande.
Pièges Examen Réseau : un Security Group ne peut JAMAIS refuser une IP spécifique (utiliser une règle Deny dans la Network ACL ou AWS WAF). Le VPC Peering n'est PAS transitif. Un VPC Gateway Endpoint évite NAT/Internet uniquement pour S3 et DynamoDB.

Amazon Route 53 : DNS, Routage Global & Résilience

Alias Records Enregistrement Alias natif AWS gratuit permettant de faire pointer le domaine Apex racine (example.com) directement vers des ressources AWS (CloudFront, ALB, NLB, bucket S3 website, API Gateway). À l'inverse d'un CNAME, il est gratuit et supporte le domaine Apex.
Politiques de routage
  • Simple : réponse DNS standard sans health check (round-robin si plusieurs IPs).
  • Weighted : répartition par pourcentage (tests A/B, migration graduelle).
  • Latency-based : oriente vers la région AWS offrant la latence minimale pour l'utilisateur.
  • Failover : basculement actif-passif (Primary/Secondary) piloté par des Route 53 Health Checks.
  • Geolocation : routage selon le pays, continent ou état de l'utilisateur.
  • Geoproximity : routage selon la proximité kilométrique avec biais (via Route 53 Traffic Flow).
  • Multi-Value Answer : renvoie jusqu'à 8 enregistrements sains choisis aléatoirement avec health check (DNS round-robin résilient).
Private Hosted Zones Zones DNS privées associées à un ou plusieurs VPCs pour la résolution interne des noms de domaines, invisible depuis l'Internet public.
Health Checks Surveillance continue d'endpoints publics (HTTP, HTTPS, TCP), alarmes CloudWatch ou combinaison d'autres checks. Inversion de statut disponible.
Piège Examen DNS : Route 53 est un serveur DNS, pas un cache web (c'est CloudFront). Les clients DNS mettent les enregistrements en cache selon le TTL : le basculement DNS n'est donc pas instantané pour les clients tant que leur TTL n'a pas expiré (utiliser AWS Global Accelerator pour un basculement sub-minute sans dépendance de TTL DNS).

Edge & Accélération : CloudFront vs Global Accelerator

Global Accelerator fournit 2 adresses IP Anycast statiques mondiales ; route le trafic au niveau L4 (TCP/UDP) directement sur le réseau dorsal AWS vers le point de présence le plus proche. Idéal pour protocoles non-HTTP (VoIP, jeux, IoT, raw TCP/UDP) et failover multi-régions quasi instantané (< 1 min via health checks intégrés).
CloudFront CDN global au niveau L7 (HTTP/HTTPS) : met en cache le contenu statique et dynamique sur 600+ Edge Locations ; TLS termination ACM (us-east-1 obligatoire), signed URLs/cookies, Origin Access Control (OAC) vers S3, WAF/Shield.

Amazon S3 Deep Dive : Stockage Objet, Classes, Sécurité & Événements

S3 Fondamentaux Objet durable (durabilité 99,999999999% - 11 9s), multi-AZ par conception, clé unique par bucket. Taille maximale d'un objet = 5 To. Forte cohérence read-after-write sur les opérations PUT et DELETE d’objets. Performance native : 3 500 PUT/POST/DELETE et 5 500 GET/HEAD requêtes/sec par préfixe.
Upload & Performance Multipart upload : recommandé dès 100 Mo et obligatoire au-delà de 5 Go (parts de 5 Mo à 5 Go, jusqu'à 10 000 parts ; parallélise et fiabilise les gros transferts). Presigned URLs : accorde un accès temporaire en lecture ou écriture sans credentials AWS. S3 Transfer Acceleration : utilise le réseau de points de présence CloudFront pour accélérer les transferts mondiaux vers S3.
Classes & Glacier Tiers
  • Standard : accès actif fréquent, latence milliseconde.
  • Intelligent-Tiering : classe idéale pour accès imprévisibles ; déplace automatiquement sans frais de récupération.
  • Standard-IA & One Zone-IA : données peu consultées (< 1x/mois), frais de lecture (One Zone-IA = 1 seule AZ, non résilient aux pannes d'AZ).
  • Glacier Instant Retrieval : archives consultées quelques fois par an avec accès milliseconde.
  • Glacier Flexible Retrieval : Expedited (1–5 min), Standard (3–5 h), Bulk (5–12 h, économique).
  • Glacier Deep Archive : Standard (12 h), Bulk (48 h, stockage le moins cher du cloud pour rétention légale 7–10 ans).
  • S3 Lifecycle Policies : automatise les transitions entre classes et la suppression après expiration.
Sécurité & Hardening S3 Block Public Access (au niveau compte et bucket) ; Bucket Policy minimale ; Object Ownership Bucket owner enforced (désactive les ACLs) ; Versioning contre suppressions accidentelles ; Object Lock / WORM impose la rétention légale en mode Governance (contournable par admin autorisé) ou Compliance (inviolable, même par root) ; Chiffrement au repos : SSE-S3 (AES-256 par défaut), SSE-KMS (contrôle de clés, rotation et audit CloudTrail) et SSE-C (clés fournies par le client).
S3 Événementiel & Requêtes S3 Event Notifications : vers SQS, SNS ou Lambda, ou via Amazon EventBridge pour tous les types d'événements et filtrage avancé. Réplication CRR/SRR : réplication continue cross-region ou same-region des nouveaux objets avec S3 RTC (Replication Time Control : 99,9% répliqués sous 15 min ; nécessite le versioning). Requêtes en place : Amazon Athena (requêtes SQL serverless sur S3) et S3 Metadata tables.
Batch Operations & MRAP S3 Batch Operations : traitement de masse à la demande (copie cross-account, re-chiffrement KMS, application de tags/Object Lock, restauration Glacier, réplication d'objets existants via S3 Batch Replication) sur des milliards d'objets via un manifest (rapport S3 Inventory ou CSV). S3 Multi-Region Access Points (MRAP) : point d'accès mondial unique fédérant plusieurs buckets régionaux avec routage automatique vers la région la plus proche et basculement dynamique.
Réflexes d’examen S3 : Objet > 5 Go → Multipart Upload obligatoire. Répliquer des objets déjà présents dans le bucket → S3 Batch Replication (CRR ne réplique que les nouveaux objets créés après son activation). Rapport d'inventaire → S3 Inventory (ne réplique rien, produit le manifest CSV). Verrouillage de conformité immuable même par root → S3 Object Lock en mode Compliance.

Stockage Bloc & Fichiers : EBS, EFS & FSx

Amazon EBS (Elastic Block Store) Stockage bloc attaché à une instance EC2. Verrouillé sur une seule AZ : ne peut pas être attaché directement à des instances dans une autre AZ (sauf snapshots ou réplication applicative). Snapshots incrémentaux sauvegardés dans S3 et chiffrables avec KMS.
Types de volumes EBS
  • gp3 : SSD polyvalent par défaut. 3 000 IOPS et 125 Mo/s inclus de base, capacité, IOPS et débit configurables indépendamment sans interruption.
  • io2 Block Express : SSD haute performance critique (jusqu'à 256 000 IOPS, durabilité 99,999%, support Multi-Attach sur une même AZ).
  • st1 : HDD Throughput Optimized pour flux séquentiels volumineux (Big Data, Data Warehouse, Kafka). Non bootable.
  • sc1 : Cold HDD pour données volumineuses rarement consultées au coût minimal. Non bootable.
Sauvegardes & Cycle de Vie Fast Snapshot Restore (FSR) rend un snapshot EBS immédiatement initialisable à performance maximale dans une AZ (pas d’effet de premier accès) ; Snapshot Archive déplace les snapshots froids vers un stockage froid moins cher (retrait 24–72 h) ; Data Lifecycle Manager (DLM) et Recycle Bin protègent contre la suppression involontaire.
Amazon EFS (Elastic File System) Système de fichiers NFS v4.1 élastique et partagé, multi-AZ par conception. Accessible simultanément par des centaines d’instances EC2 et conteneurs/fonctions Lambda. Classes EFS Standard, EFS Infrequent Access (EFS IA) et EFS Archive avec Lifecycle Management pour réduire les coûts des fichiers froids.
Famille Amazon FSx
  • FSx for Windows File Server : partage SMB natif, NTFS, quotas et intégration Active Directory d'entreprise.
  • FSx for Lustre : système de fichiers POSIX ultra-haut débit et latence sub-milliseconde optimisé pour HPC, ML et couplage direct avec Amazon S3.
  • FSx for NetApp ONTAP : multi-protocole (NFS, SMB, iSCSI), déduplication, compression et snapshots NetApp.
  • FSx for OpenZFS : stockage ZFS Linux managé avec millions d’IOPS.
Repères d'Arbitrage : EBS = stockage bloc haute performance attaché à une seule AZ. EFS = système de fichiers POSIX partagé multi-AZ pour Linux et Lambda. FSx = partages d'entreprise spécialisés (Windows SMB ou Lustre HPC). Ne jamais tenter de monter un volume EBS standard simultanément sur plusieurs AZ.

Volume Gateway (Cached) iSCSI Données principales dans S3 ; blocs fréquemment lus conservés en cache local.

AWS Transfer Family serveurs managés haute disponibilité SFTP, FTPS et FTP pour charger/extraire des fichiers directement dans des buckets S3 ou systèmes de fichiers EFS sans gérer d'infrastructure EC2 ni d'authentification personnalisée.
AWS DataSync service de transfert réseau accéléré (jusqu'à 10x plus rapide qu'un transfert standard) pour synchroniser en continu ou à la demande entre serveurs on-prem (NFS, SMB) et services AWS (S3, EFS, FSx) avec intégrité de données et planification intégrées.
Règle de décision : Accès hybride continu avec cache local on-premise → Storage Gateway. Transfert et synchronisation réseau récurrente ou planifiée de gros volumes de fichiers → AWS DataSync. Protocoles SFTP/FTPS managés pour partenaires externes → AWS Transfer Family.

Compute EC2 : Modèles d'Achat, Auto Scaling & Placement Groups

EC2 Instances Choisir une famille selon CPU (C), mémoire (R), général (M), stockage local NVMe (I/D), GPU (G/P) ou burstable (T avec CPU credits). User data automatise le bootstrap ; AMI et Launch Template rendent le déploiement reproductible et versionné.
Modèles d'achat On-Demand : flexibilité maximale sans engagement ; Reserved Instances / Savings Plans : 30–72% de remise contre engagement 1 ou 3 ans (Compute Savings Plans flexible sur EC2/Fargate/Lambda vs EC2 Instance Plans verrouillé sur une région/famille) ; Spot : jusqu'à 90% d'économie sur la capacité excédentaire interruptible avec préavis de 2 minutes (batch, workers, charges tolérantes aux pannes).
Hibernation & Réservations EC2 Hibernate : sauvegarde l’état de la RAM sur le volume EBS root chiffré pour reprise en quelques secondes sans reboot complet (max 60 jours). On-Demand Capacity Reservations : réserve la capacité physique d'instances dans une AZ spécifique (sans remise financière, combinable avec Savings Plans).
ASG (Auto Scaling Group) groupe d’instances décrit par un Launch Template avec min / desired / max, réparti sur plusieurs AZ pour éliminer le SPOF. Un health check EC2 ou ELB remplace automatiquement les instances en mauvaise santé. S'attache à un ELB pour recevoir le trafic.
Élément ASG Rôle clé
Launch Template AMI, type d’instance, user data, EBS, security group ; versionné et recommandé.
min / desired / max Bornent la capacité ; desired est la cible initiale, ajustée par les politiques de scaling.
Multi-AZ Instances réparties équitablement entre AZs ; tolérance aux pannes d'AZ native.
Health checks EC2 / ELB Remplacement automatique des instances déclarées « unhealthy ».
Lifecycle hooks Pause avant launch ou terminate (actions de bootstrap, drainage de connexions).

Placement Groups contrôlent la disposition physique sur le matériel AWS :
  • Cluster : instances regroupées sur le même rack dans une seule AZ pour ultra-basse latence et très haut débit (HPC, Big Data).
  • Spread : instances sur du matériel physique totalement distinct pour isolation maximale des pannes (limite stricte de 7 instances par AZ).
  • Partition : instances réparties sur des segments logiques à racks indépendants (jusqu’à 7 partitions par AZ) pour allier grand scale et tolérance aux pannes (Hadoop, Kafka, Cassandra).
Elastic Load Balancing (ELB) ALB (Application Load Balancer) : L7 HTTP/HTTPS, routage par URL/path/host, WAF, redirection HTTPS et auth OIDC/Cognito. NLB (Network Load Balancer) : L4 TCP/UDP/TLS, performance extrême, latence microseconde et IP statique Anycast/Elastic IP. Gateway Load Balancer : L3/L4 pour insertion transparente d’appliances réseau tierces (firewalls).
Pièges Examen EC2 & ASG : Scheduled scaling est statique : il applique une capacité à une heure T sans mesurer la charge réelle, un pic imprévu ne sera pas absorbé sans Target Tracking en renfort. Remplacer une instance unhealthy n'est pas du scaling : c'est du maintien de capacité. Une instance Spot ne doit jamais héberger une base de données critique solo sans réplication.

Conteneurs AWS : ECS, EKS & Fargate Deep Dive

AWS Fargate Moteur de calcul serverless (« Le Muscle », pas un orchestrateur autonome) : alloue CPU et mémoire à la demande et masque toute l'infrastructure (serveurs, OS, patchs, scaling de VM). Principe fondamental : Fargate n'a aucune API ni console directe pour lancer des conteneurs isolés, aucun routage web natif ni d'autoscaling autonome. C'est le moteur d'exécution (le « muscle ») qui doit impérativement être instruit et piloté par un orchestrateur (le « cerveau ») : Amazon ECS (Elastic Container Service) ou Amazon EKS (Elastic Kubernetes Service).
AWS App Runner (legacy) Fermé aux nouveaux clients depuis le 31 mars 2026 : ce PaaS de conteneurs web 1-clic (équivalent Google Cloud Run avec URL HTTPS/TLS et scale-to-zero automatiques) est remplacé par ECS + Fargate derrière un ALB (ou API Gateway) pour les APIs web, et par Lambda + API Gateway pour les charges événementielles légères.
Amazon ECS (Compute Options) orchestrateur de conteneurs natif AWS, simple et hautement intégré :
  • AWS Fargate : conteneurs serverless avec zéro gestion de serveurs sous-jacents.
  • Amazon EC2 Instances : machines virtuelles traditionnelles gérées par le client (Capacity Providers, Auto Scaling Groups, AMI et patchs OS).
  • External Instances (ECS Anywhere) : serveurs physiques locaux on-premises ou VMs externes rattachés au control plane central ECS.
Amazon EKS (Compute Options) service Kubernetes managé par AWS pour la portabilité et les écosystèmes open-source :
  • AWS Fargate : pods Kubernetes serverless isolés au niveau VM et gérés via des Fargate Profiles.
  • EKS Managed Node Groups : instances EC2 dont AWS automatise le provisioning, le cycle de vie et les mises à jour de sécurité des AMIs.
  • Self-Managed EC2 Nodes : instances EC2 configurées manuellement et jointes au cluster pour un contrôle bas niveau maximal.
  • Karpenter : autoscaler de nœuds open-source haute performance qui provisionne instantanément les types d'instances EC2 optimaux selon les besoins des pods en attente (bypasse les groupes ASG et le Cluster Autoscaler standard).
  • Hybride / Outposts / EKS Anywhere : exécution de pods Kubernetes sur matériel on-premises ou racks AWS Outposts.
ECS IAM Roles Task Role = permissions accordées au code applicatif du conteneur (S3, DynamoDB) ; Task Execution Role = permissions accordées à l'agent ECS (pull d'images ECR, envoi des logs CloudWatch, déchiffrement de secrets KMS/SSM).
ECS Networking mode awsvpc recommandé (chaque tâche reçoit sa propre ENI et Security Group dédié, obligatoire sur Fargate).
Arbitrage : ECS + Fargate vs Lambda vs EKS
  • Workloads non-HTTP : ECS gère les workers d'arrière-plan, consommateurs de files (SQS, Kafka/MSK), tâches cron planifiées et pipelines batch.
  • Multi-conteneurs (Sidecar Pattern) : les tâches ECS permettent la colocalisation de conteneurs partageant localhost (ex: application + proxy Envoy + collecteur de logs/métriques Datadog/OTel).
  • Contrôle réseau fin (awsvpc) : ENI et Security Group dédiés par tâche ECS, micro-segmentation VPC granulaire et intégration PrivateLink.
  • FinOps & Fort Volume : ECS offre Fargate Spot (jusqu'à -70%), Savings Plans et Capacity Providers mixtes, tandis que Lambda reste optimal pour les charges événementielles courtes.

Piège Examen Conteneurs : Fargate = moteur de calcul serverless (« muscle », pas d'orchestration autonome directe) ; Lambda = exécution événementielle sans serveur, sans cluster ni load balancer à gérer ; ECS = simplicité native AWS, sidecars & workers non-HTTP ; EKS = standard Kubernetes & portabilité ; Karpenter = autoscaling dynamique de nœuds EKS sans ASG. Les PaaS de conteneurs web 1-clic (App Runner) sont fermés aux nouveaux clients : cibler ECS + Fargate derrière un ALB.

Serverless Compute & APIs : AWS Lambda, API Gateway & AppSync

AWS Lambda Exécution événementielle sans serveur facturée à la milliseconde. Limites d'exécution : durée maximale = 15 minutes ; mémoire de 128 Mo à 10 240 Mo (10 Go) avec CPU proportionnel ; stockage temporaire /tmp de 512 Mo à 10 Go ; package zippé 50 Mo / 250 Mo décompressé (jusqu'à 10 Go via image conteneur ECR).
Concurrence & Cold Starts Provisioned Concurrency : pré-alloue les environnements d'exécution pour éliminer totalement le cold start sur les APIs sensibles à la latence. Reserved Concurrency : plafonne la concurrence maximale allouée à une fonction pour protéger les bases de données aval contre l'épuisement de connexions.
Lambda en VPC Privé Utilise les ENIs Hyperplane (attachement instantané). Requiert impérativement un NAT Gateway dans un subnet public ou des Interface VPC Endpoints pour joindre Internet ou des services AWS sans passer par le réseau public.
Amazon API Gateway
  • HTTP APIs : nouvelle génération ultra-rapide et économique (-70%), support natif OIDC et JWT Cognito, CORS facile.
  • REST APIs : fonctionnalités avancées : intégration AWS WAF, validation de schéma JSON de requêtes, API Keys et Usage Plans (throttling/quotas), cache d'API en mémoire, transformations VTL.
  • WebSocket APIs : connexions bidirectionnelles persistantes temps réel (chat, alertes, tableaux de bord).
AWS AppSync Service GraphQL managé avec subscriptions WebSocket temps réel natives, cache d'API et résolveurs directs vers DynamoDB, Lambda, Aurora ou APIs HTTP sans code serveur intermédiaire.
Arbitrage Serverless : Traitement court (< 15 min), événementiel, asynchrone ou à trafic variable → AWS Lambda. Traitements longs (> 15 min), workers continus ou charge stable 24/7 → ECS + Fargate. API simple/économique → HTTP API ; API avec WAF, clés et plans d'usage → REST API.

Worker Tier : file SQS + démon d'arrière-plan tirant les messages pour exécuter des jobs lourds. Personnalisation avancée via fichiers .ebextensions dans le code source.

Bases de Données & Caches : Relationnel, NoSQL & In-Memory

RDS (Relational Database Service) Moteurs relationnels managés (PostgreSQL, MySQL, Oracle, SQL Server). Multi-AZ : réplication synchrone vers une instance standby dans une autre AZ avec failover DNS automatique en 60–120s pour la haute disponibilité (le standby ne sert pas de cible de lecture). Read Replicas : réplication asynchrone pour scaler les lectures (jusqu'à 15 réplicas, peuvent être multi-régions ou promues en cas de sinistre).
Amazon Aurora Architecture cloud-native découplant compute et stockage. Stockage distribué répliqué sur 3 AZ en 6 copies avec réparation continue. Endpoints reader/writer automatiques. Aurora Serverless v2 : ajuste instantanément les ACUs selon la charge. Aurora Global Database : réplication cross-région < 1s et failover en < 1 min pour DR. Backtrack : rembobine la base à la seconde près en quelques minutes sans restaurer de snapshot. Fast Cloning : clone copy-on-write instantané.
RDS Proxy Pool de connexions managé haute disponibilité placé devant RDS et Aurora. Protège la base contre l'épuisement des pools de connexions provoqué par des milliers d'invocations Lambda ou conteneurs concurrents. Réduit l'overhead TLS et divise par 3 le temps de failover Multi-AZ.
Amazon DynamoDB Base NoSQL clé-valeur et document managée ultra-rapide. Partition key bien distribuée à haute cardinalité pour éviter les « hot partitions ». Capacité : On-Demand (charge imprévisible ou spiky) vs Provisioned (avec Auto Scaling de RCU/WCU). Index : GSI (Global Secondary Index, nouvelle partition key, asynchrone) vs LSI (Local Secondary Index, même partition key, créée à la création de table).
Accélération DynamoDB DAX (DynamoDB Accelerator) : cache en mémoire transparent offrant une latence microseconde en lecture. Global Tables : réplication active-active multi-régions entièrement managée. TTL : expiration et suppression automatique gratuite d'éléments sans consommer de WCU. TransactWriteItems : transactions ACID multi-tables coordonnées.
ElastiCache & MemoryDB Amazon ElastiCache : Redis (structures riches, clustering, réplication/failover multi-AZ et persistance) vs Memcached (cache mémoire simple multithreadé sans persistance). Amazon MemoryDB for Redis : base de données NoSQL compatible Redis entièrement en mémoire et 100% durable grâce à un journal de transactions multi-AZ.
Moteurs Spécialisés Redshift : data warehouse analytique colonnaire (OLAP, requêtes SQL via Spectrum directement sur S3). OpenSearch : recherche full-text et analyse de logs. Neptune : base de données graphe (Property Graph, RDF). DocumentDB : compatible MongoDB. Timestream for InfluxDB : séries temporelles (Timestream for LiveAnalytics fermé aux nouveaux clients depuis le 20 juin 2025).
Choix rapide : Transactions relationnelles complexes = RDS / Aurora ; Clé-valeur à très grande échelle et latence milliseconde = DynamoDB ; Cache de lecture en mémoire = ElastiCache (Redis) ou DAX ; Épuisement de connexions Lambda = RDS Proxy ; Data warehouse analytique = Redshift.

Messaging, Événements & Orchestration Applicative

Amazon SQS (Simple Queue Service) File d'attente de messages managée pour découpler les systèmes. Limites : payload max = 256 Ko (jusqu'à 2 Go via la librairie S3 Extended Client) ; rétention de 1 minute à 14 jours (4 jours par défaut) ; Visibility Timeout : durée pendant laquelle un message consommé est masqué aux autres workers (défaut 30s, max 12h) ; Long Polling : ReceiveMessageWaitTimeSeconds jusqu'à 20s pour réduire les coûts ; Dead-Letter Queue (DLQ) : isole les messages en échec après maxReceiveCount tentatives.
Service Modèle Décision d’architecture
SQS Standard Queue, at-least-once Découplage et débit quasi illimité ; les messages peuvent arriver en double (idempotence côté consumer requise).
SQS FIFO Ordre strict / déduplication MessageGroupId pour ordonner par flux, MessageDeduplicationId ; débit max 300 msg/s (3 000 avec batch).
Amazon SNS Pub/sub fan-out Publier vers de multiples abonnés (SQS, Lambda, HTTPS, email) ; filtrage de messages par attributs JSON.
Amazon EventBridge Bus d'événements serverless Routage puissant par règles JSON, intégration native 200+ services AWS, SaaS (Salesforce) et custom apps, archive/replay et schema registry.
AWS Step Functions Orchestration visuelle State Machines avec retries, branches, parallélisme et saga compensation. Standard (> 1 an, exactly-once) vs Express (fort débit < 5 min).
Pattern robuste : Producteur → SNS ou EventBridge → Fan-out vers plusieurs files SQS dédiées (avec Dead-Letter Queue) → consumers idempotents. Une Dead-Letter Queue facilite l’analyse sans perdre les messages après des retries épuisés.

Streaming de Données : Amazon Kinesis Suite & Amazon MSK

Kinesis Data Streams le streaming temps réel en mode pull : les données sont ingérées dans des shards (1 Mo/s d’écriture, 2 Mo/s de lecture par shard) et consommées par des applications custom (KCL, Lambda, Spark, Flink). L’ordre est garanti par shard grâce à la partition key. Rétention 24 h par défaut jusqu’à 365 jours, mode at-least-once (consommateurs idempotents). Redimensionnement par SplitShard / MergeShards et Enhanced Fan-Out (EFO) (2 Mo/s dédiés par consommateur avec latence HTTP/2 < 70 ms).
Kinesis Data Firehose livraison managée near real-time en mode push : aucun code consommateur, un buffer (1 Mo à 128 Mo, 60 à 900 s) est vidé vers S3, Redshift (via S3 COPY), OpenSearch, Splunk ou un endpoint HTTP personnalisé. Supporte la transformation Lambda à la volée, la conversion de format (JSON vers Parquet / ORC) et le partitionnement dynamique S3.
Kinesis Data Analytics (Flink) analyse en continu et temps réel des flux de streaming : exécution de requêtes SQL streamées ou applications Apache Flink managées (Java, Scala, Python) ; fenêtrage temporel (tumbling, sliding, session windows), détection d'anomalies ML et enrichissement des flux avant réémission vers S3, Firehose ou Data Streams.
Kinesis Video Streams ingestion, stockage sécurisé et diffusion de flux vidéo et audio en direct (caméras de sécurité, capteurs IoT, drones) ; supporte WebRTC pour des communications interactives bidirectionnelles à ultra-faible latence ; l'analyse visuelle se fait avec Amazon Rekognition Image appliqué aux frames extraites du flux (le streaming vidéo managé Rekognition est fermé aux nouveaux clients depuis le 30 avril 2026).
Amazon MSK Apache Kafka managé (brokers multi-AZ, connecteurs Kafka Connect, MSK Serverless) pour les architectures nécessitant une compatibilité standard open-source Kafka sans administrer les clusters d'infrastructure.
Service Modèle Latence Cas d’usage typique & Cible
Data Streams Pull (shards / KCL) Temps réel (< 200 ms / 70 ms EFO) Événements temps réel, ordre par clé, consommateurs multiples avec checkpointing.
Data Firehose Push (buffer managé) Near real-time (60s à 900s) Ingestion sans code et conversion Parquet vers S3, Redshift, OpenSearch.
Data Analytics Stream Processing (Flink) Sub-seconde en continu Calculs d'agrégations, fenêtres temporelles, ML et alertes sur flux.
Video Streams Video / WebRTC Temps réel interactif Caméras IoT, frames analysées par Rekognition Image, audio/vidéo bidirectionnel.
Amazon MSK Pub/Sub Kafka (topics) Temps réel milliseconde Compatibilité Kafka existante, écosystème connecteurs Kafka, contrôle fin des brokers.
Piège Examen Kinesis : Firehose bufferise toujours (ce n'est pas du temps réel pur sub-seconde et ce n'est pas consommable en pull par du code custom) ; l'ordre dans Data Streams n'est garanti que par shard (pas globalement comme SQS FIFO) ; en cas de throttling ProvisionedThroughputExceededException, ajouter des shards ou utiliser une partition key avec une cardinalité plus élevée.

Amélioration — 25% diagnostiquer une architecture existante, supprimer la dette opérationnelle, augmenter la résilience et optimiser le coût sans régression.
Migration — 20% choisir le bon 7R, réduire le downtime, traiter les dépendances et automatiser cutover, validation et rollback.
Réflexe SAP : plusieurs réponses peuvent être techniquement possibles. Retenir celle qui respecte toutes les contraintes, minimise l’effort opérationnel, limite le domaine d’impact d’une erreur (plus petit blast radius) et rend la sécurité explicite.

Landing zone, multi-comptes & automatisation

Organizations Root → OUs → comptes : management, log archive, security tooling, network/shared services, workloads dev/test/prod pour réduire le blast radius et clarifier la facturation. Le management account reste minimal : activer MFA, protéger l'accès root, ne jamais y héberger de workload.
Control Tower Automatise la landing zone, Account Factory et guardrails. Guardrails preventive = SCP (empêchent l'action) ; detective = AWS Config (constatent la dérive mais ne bloquent pas la création initiale) ; proactive = CloudFormation Hooks. Une SCP bloque mais n’accorde jamais un droit IAM (Identity and Access Management).
IAM Identity Center SSO centralisé vers les comptes et permission sets. Pour machine-to-machine, STS AssumeRole et credentials temporaires, jamais une access key partagée.
Audit central Organization CloudTrail vers le compte Log Archive : bucket S3 à policy restrictive, Object Lock, versioning et écriture réservée aux services, séparation des rôles. Config Aggregator consolide la conformité ; delegated administrators (GuardDuty, Security Hub, Inspector, Macie, IAM Access Analyzer) centralisent les findings et automatisent leur traitement.
Network / Shared Services Transit Gateway, DNS Resolver, endpoints, inspection, Active Directory, CI/CD et services partagés dans des comptes dédiés.
Automatisation StackSets déploie les templates sur chaque nouveau compte d'une OU ; Service Catalog fournit des portfolios avec Launch Constraints (délégation de droits IAM de déploiement) ; License Manager applique les quotas de licences (vCPU/cores). Politiques d'Organisation : Tag Policies (standardisation des clés/valeurs), Backup Policies (sauvegardes obligatoires), AI Opt-Out.
FinOps AWS Budgets, Cost Categories/Allocation Tags et Billing Conductor pour visibilité et showback/chargeback entre business units.
SAP Gotcha : ne pas placer toutes les workloads dans un compte unique « pour simplifier ». Le multi-compte isole permissions, quotas, logs, facturation et pannes ; une SCP mal appliquée peut toutefois casser les opérations d’un OU entier. Les SCPs ne s'appliquent jamais au Management Account.

Réseau entreprise : Transit Gateway, Direct Connect & Cloud WAN

Transit Gateway : routage hub régional pour VPC attachments, VPN et Direct Connect. Séparer associations et propagations dans plusieurs route tables (prod/shared/inspection) : prod peut atteindre shared-services sans exposer dev ; documenter routes effectives et blackholes.
Central egress private subnets → Transit Gateway → egress VPC → NAT Gateway/Network Firewall → Internet Gateway. Déployer NAT et endpoints dans plusieurs AZ et contrôler le chemin retour.
Inspection inspection VPC via Gateway Load Balancer ou AWS Network Firewall (filtrage east-west/north-south) ; appliance VPC/Gateway Load Balancer → retour symétrique obligatoire pour une appliance stateful : activer Transit Gateway Appliance Mode sur l'attachement.
RAM (Resource Access Manager) partager Transit Gateway, subnets ou autres ressources avec des comptes/OU sans créer de peering full mesh ; le partage ne contourne ni IAM (Identity and Access Management) ni routes.
Direct Connect Gateway relie des Direct Connect locations aux VPC via transit/private Virtual Interface ; annoncer uniquement les préfixes nécessaires et respecter les limites BGP (100 routes max).
Direct Connect : résilience & chiffrement Maximum Resiliency (2 liaisons sur 2 sites Direct Connect distincts) vs High Resiliency (2 liaisons sur 1 site) ; LAG agrège jusqu'à 4 liaisons physiques actives/actives (LACP) ; SiteLink connecte les sites on-prem via le réseau dorsal AWS. Direct Connect est privé mais pas chiffré par défaut : MACsec au débit nominal 10G/100G ou VPN IPsec sur Direct Connect (public Virtual Interface + VPN public, ou transit Virtual Interface + VPN à IP privée selon le design).
BGP Communities communautés BGP AWS (7224:7100 Low, 7224:7200 Med, 7224:7300 High) et AS-Path Prepending pour influencer le chemin retour.
Direct Connect + VPN Direct Connect fournit le chemin primaire, VPN Site-to-Site redondant le backup ; deux tunnels terminés sur deux AZ/points de terminaison différents évitent un SPOF.
Cloud WAN politique réseau globale déclarative par segments (Core Network Policy) : privilégier pour un WAN mondial ; Transit Gateway reste le choix régional classique pour connecter VPC, VPN et Direct Connect.
SAP Gotcha : une route annoncée dans Transit Gateway ne garantit pas le chemin retour. Vérifier les tables de routes VPC, Transit Gateway, appliance, Direct Connect/VPN et les filtres BGP dans les deux directions.

Hybrid DNS & PrivateLink

Route 53 Resolver inbound permet au DNS on-prem de résoudre les zones privées AWS via endpoints ENI. Outbound : transmet les requêtes AWS vers les resolvers on-prem avec forwarding rules partagées par RAM (Resource Access Manager).
Resolver rules centraliser les règles dans un compte réseau et les partager avec RAM. Attention aux boucles de forwarding, à la résolution conditionnelle et aux security groups des endpoints.
Route 53 Resolver DNS Firewall filtrer les requêtes DNS selon le domaine pour bloquer l’exfiltration via DNS et l’accès à des domaines malveillants, en mode managé/multi-comptes ; s’applique aux endpoints Resolver et aux VPC.
Private Hosted Zone associer à plusieurs VPC (ou architecture centralisée selon le besoin). Une zone publique et privée de même nom ont des réponses différentes selon le point de résolution.
PrivateLink provider → NLB (Network Load Balancer) → endpoint service ; consumer → interface endpoint. Accès unidirectionnel au service, sans route réseau globale ni CIDR non chevauchant requis.
Overlapping CIDR éviter Peering/Transit Gateway IP routing. PrivateLink résout l’exposition service-to-service ; Private NAT peut traduire des flux bidirectionnels quand une vraie connectivité IP est nécessaire.
SAP Gotcha : PrivateLink n’est pas un transit VPC généraliste et ne fournit pas une résolution DNS « magique ». Publier le nom privé, configurer endpoint DNS et autoriser le SG/NLB.

KMS, conformité & cross-account

KMS (Key Management Service) key policy dans un compte sécurité : autoriser l’utilisation par le compte consommateur (Principal: arn:aws:iam::CompteB:root), puis la policy IAM (Identity and Access Management) du rôle consommateur doit aussi permettre l’action. Les deux portes sont nécessaires.
Multi-Region keys clés répliquées avec même key material/logical key ID pour déchiffrer localement des données répliquées sans appel réseau distant ; elles ne remplacent pas la stratégie de réplication ni les contrôles d’accès.
S3 replication & KMS SRR/CRR, versioning sur les deux buckets, IAM role de réplication, KMS grants/key policy cross-account et ownership/ACL adaptés. Re-encryption KMS nécessaire lors d’un changement de clé.
SCP vs key policy une SCP peut bloquer l’appel KMS même si key policy et IAM autorisent ; la policy KMS ne peut pas outrepasser une SCP.
Compliance Config conformance packs et Security Hub standards pour les contrôles, Macie pour la détection de PII dans S3, CloudTrail (management + data events) exporté vers S3 pour la conservation longue, puis Athena, CloudWatch Logs Insights ou OpenSearch pour l'analyse (Audit Manager et CloudTrail Lake sont fermés aux nouveaux clients depuis le 31 mars 2026).
KMS External Key Store (XKS) lorsque la règle métier exige que le matériel de clé ne quitte jamais un HSM contrôlé par le client : CloudHSM (HSM dédié) ou External Key Store (XKS) relie KMS à un HSM externe pour conserver les opérations KMS standards côté AWS.
SAP Gotcha : cocher « encryption enabled » ne suffit pas. Vérifier région de la clé, grants, key policy, rôle de réplication, destination cross-account et capacité à restaurer.

DR d’entreprise : RTO/RPO

RTO & RPO temps de remise en service ; RPO fenêtre de perte. Définir les objectifs par application et classer les dépendances (DNS, IAM, secrets, réseau, données, observabilité).
Modèle Implémentation AWS Arbitrage
Backup & restore AWS Backup, S3 CRR, IaC, snapshots cross-Region Moins cher, RTO élevé ; valider les runbooks.
Pilot light RDS/Aurora réplica, données synchronisées, stack minimale RPO bas, compute à démarrer ; activation orchestrée.
Warm standby Stack réduite active, ASG scale-out, Route 53 failover RTO faible et coût intermédiaire.

Résilience opérationnelle (DRS / FIS)

Elastic Disaster Recovery (DRS) réplication continue au niveau bloc de serveurs on-prem ou EC2 vers une staging area légère et lancement de l’infrastructure de reprise à la demande ; RPO en secondes et RTO en minutes.
Resilience Hub évalue les objectifs de résilience d’une application, identifie les écarts et propose des recommandations ; il ne remplace pas les tests de failover.
AWS Backup Vault Lock impose une rétention immuable en mode compliance ; combiner copies cross-account/cross-Region et politiques Organizations.
FIS (Fault Injection Service) teste volontairement des défaillances (chaos engineering) ; limiter l’expérimentation par IAM, tags, Stop Conditions CloudWatch automatiques et fenêtres approuvées.
Runbook inclure quotas, IAM, secrets, certificats ACM, DNS/TTL, réplication, dépendances tierces, observabilité, validation métier et procédure de retour arrière.
Réponse aux incidents CloudWatch Alarms et EventBridge déclenchent AWS Chatbot / Amazon SNS pour le paging des personnes de garde, les runbooks SSM Automation pour l'auto-résolution et l'ouverture de tickets vers l'outil de gestion de service ; l'historique et le post-incident review s'appuient sur CloudWatch et CloudTrail (SSM Incident Manager est fermé aux nouveaux clients depuis le 7 novembre 2025). À distinguer de CloudWatch (métriques/alarmes) et d'AWS Health (événements AWS) : ces briques orchestrent la réponse humaine.
SAP Gotcha : une architecture multi-AZ ne suffit pas si le déploiement, les quotas régionaux, les secrets ou les permissions de restauration restent dans une seule région.

Usine de Migration, Découverte & Transfert Hybride de Données

Discover & TCO Migration Evaluator modélise le TCO, collecte l'inventaire (agent dédié ou agentless) et cartographie les processus et dépendances réseau avant migration. Il remplace l'Application Discovery Service (ADS), fermé aux nouveaux clients depuis le 7 octobre 2025 ; AWS Transform et partenaires complètent l'analyse applicative.
Migration Factory Landing zone, comptes, réseau, IAM, logging et templates IaC prêts avant la première vague. Standardiser AMI, tags, backup, monitoring et rollback. Le pilotage des vagues se fait directement dans l'Application Migration Service (MGN) et Database Migration Service (Migration Hub fermé aux nouveaux clients depuis le 7 nov 2025 ; SMS en fin de support depuis 2023).
Data Migration Protocol Full load → CDC → validation des compteurs/checksums → gel court des écritures → cutover → observation post-bascule. Mesurer le lag de réplication CDC en continu.
Transfert Réseau Accéléré AWS DataSync : pour transferts récurrents et vérifiés (10x plus rapide) vers S3/EFS/FSx ; Storage Gateway : pour accès hybride continu avec cache local on-premises.
Transfert Physique de Masse AWS Data Transfer Terminal pour apporter/retirer les supports en toute sécurité, dispositifs partenaires du Marketplace pour l'offline de masse. Legacy : la famille Snow (Snowcone, Snowball Edge, Snowmobile) n'est plus commandable pour les nouveaux clients (Snowball Edge fin de support nov 2025, Snowmobile mars 2024). Retenir DataSync / Data Transfer Terminal / Outposts.
Hybrid Edge AWS Outposts (racks AWS natifs on-prem), AWS Local Zones (faible latence métropolitaine), AWS Wavelength (compute 5G).
SAP Gotcha : réduire le downtime ne signifie pas supprimer la validation. Une migration sans mesure de CDC lag, tests de cohérence et plan de rollback n’est pas maîtrisée.

CloudFormation d'Entreprise & IaC

CloudFormation StackSets déploie et met à jour des stacks de manière centralisée à travers plusieurs comptes et plusieurs régions AWS en une seule opération ; s'intègre nativement avec AWS Organizations pour auto-déployer automatiquement sur tout nouveau compte ajouté dans une OU.
Gestion du cycle de vie DeletionPolicy (Retain pour préserver S3/RDS lors de la suppression de stack, Snapshot pour créer un snapshot de sauvegarde, Delete) et UpdateReplacePolicy.
Stack Policies politiques JSON attachées aux stacks pour interdire explicitement les mises à jour accidentelles de ressources critiques (ex: interdire la modification d'un cluster RDS de production).
Custom Resources permet d'écrire des scripts d'extension personnalisés déclenchés par Lambda lors des opérations CRUD du stack (ex: provisionner un certificat tiers, initialiser une base de données).
Architecture modulaire Nested Stacks (sous-stacks réutilisables orchestrés par un template parent) vs Cross-Stack References (Export et Fn::ImportValue pour partager des identifiants d'infrastructures communes, comme les VPC IDs). Drift Detection identifie les modifications manuelles hors IaC.

Architecture event-driven, API & Modernisation

EventBridge bus central et règles par événement pour découpler domaines. Archive/replay et schema registry aident la gouvernance des contrats. Supporte événements AWS, SaaS (Salesforce) et custom.
SQS (Simple Queue Service) buffer de back-pressure avec visibilité, retry et Dead-Letter Queue. Garantir idempotence car Standard est at-least-once ; FIFO seulement si ordre/déduplication nécessaires.
SNS & Step Functions SNS : fan-out vers plusieurs consommateurs ; combiner SNS→SQS pour isoler les vitesses de traitement. Step Functions : gère workflow et compensation (Saga pattern). Standard vs Express.
Conteneurs & Modernisation ECS + Fargate derrière un ALB pour les APIs web et les architectures d'entreprise (sidecars, workers SQS/batch, micro-segmentation awsvpc) ; EKS pour gouvernance Kubernetes/portabilité multi-cloud. Utiliser Fargate Spot et Savings Plans pour charges continues.
SAP Gotcha : un bus d’événements n’est pas une file de travail. Utiliser EventBridge pour router, SQS pour retenir jusqu’à consommation et Step Functions pour orchestrer plusieurs étapes.

Améliorer une solution existante : FinOps & Well-Architected

Well-Architected analyser Operational Excellence, Security, Reliability, Performance Efficiency, Cost Optimization et Sustainability ; utiliser AWS Trusted Advisor et les métriques réelles avant de changer.
Observability centraliser CloudWatch cross-account, X-Ray, CloudTrail organization trail, Config Aggregator et Security Hub. Corréler logs, traces, métriques et événements de déploiement.
Performance cache CloudFront/ElastiCache, read replicas, DynamoDB partition design, async queues, compression et placement régional ; ne pas scaler verticalement par réflexe.
Cost rightsizing, Graviton, Savings Plans, Spot, S3 Lifecycle, endpoints, réduction du trafic cross-AZ et extinction des environnements non production.
Operations IaC CloudFormation/CDK/Terraform, pipelines CI/CD, immutable AMI, Systems Manager Patch Manager/Automation et runbooks testés plutôt que scripts manuels.
Compute Optimizer recommande le rightsizing (type/famille d’instance, droits Graviton) à partir de l’usage réel via apprentissage automatique, y compris cross-account grâce au delegated admin.
Personal Health Dashboard / Health API alertes proactives sur les événements AWS (maintenance planifiée, pannes régionales) affectant vos ressources, avec vue organisationnelle ; ne pas confondre avec le statut global (Service Health Dashboard).

Data platform, Big Data & analytics

Cas d’entreprise — décisions à haute valeur

Banque mondiale : séparation réglementaire et reprise

Contraintes

  • Comptes prod séparés par région/régulateur, journaux immuables (WORM 7 ans) et accès opérateur fédéré.
  • RPO de quelques minutes et RTO inférieur à 15-30 minutes pour les bases critiques.

Architecture

Control Tower → OUs réglementaires → Identity Center avec MFA ; CloudTrail/Config/GuardDuty/Security Hub centralisés vers Log Archive avec S3 Object Lock ; Aurora Global/DynamoDB Global Tables selon le modèle de données ; Route 53 ARC / Global Accelerator pour le failover.
SAP Gotcha : la réplication multi-région n’est pas une garantie de cohérence transactionnelle universelle. Choisir le datastore selon les writes, conflits et exigences ACID. Pour écritures multi-régions simultanées, DynamoDB Global Tables.
Groupe industriel : datacenter, CIDR chevauchants et modernisation

Contraintes

  • Plusieurs sites avec CIDR historiques identiques, liaison Direct Connect principale avec redondance maximale et VPN de secours.
  • Exposer progressivement des APIs migrées sans connecter les réseaux entiers.

Architecture

Direct Connect redondant (Maximum Resiliency) + VPN → Direct Connect Gateway/Transit Gateway pour les préfixes non conflictuels avec VPC d'inspection centrale (Gateway Load Balancer / Appliance Mode) ; PrivateLink (NLB + endpoint service) pour les services aux CIDR conflictuels ; Application Migration Service / Database Migration Service / Schema Conversion Tool pour migrer ; ECS/Fargate + EventBridge/SQS pour moderniser.
SAP Gotcha : PrivateLink expose un service, il ne résout pas une dépendance qui exige une connectivité IP bidirectionnelle complète. Pour cette dernière, examiner Private NAT et la re-numérotation.
Retail global : trafic variable et coûts

Contraintes

  • Pics saisonniers (Black Friday 50x), catalogue mondial, recherche rapide, données client chiffrées et équipes autonomes.
  • Éviter le sur-provisionnement et isoler les coûts par domaine.

Architecture

CloudFront + WAF en edge → API Gateway/Lambda ou ECS Fargate → DynamoDB Global Tables avec DynamoDB Accelerator(DAX) pour accès clé-valeur mondial ; SQS FIFO + Step Functions pour commandes ; Cost Allocation Tags/Budgets pour FinOps.
SAP Gotcha : ne pas choisir une base relationnelle uniquement parce que les données sont « importantes ». Le pattern d’accès, les transactions et la cohérence décident du service.
