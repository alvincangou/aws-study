SAA-C03 : méthode & Well-Architected

Sécurité identité, privilège minimal, chiffrement, segmentation et traçabilité avant toute optimisation.
Résilience supprimer les SPOF, répartir sur plusieurs AZ, découpler et prévoir la restauration testée. Multi-AZ protège d’une panne d’AZ ; multi-Region protège d’une panne régionale.
Performance choisir selon le pattern d’accès, la latence, le débit, la taille et la cohérence ; préférer cache, asynchronisme et scale-out au surdimensionnement.
Coût comparer coût fixe/variable, trafic inter-AZ, stockage, licences et effort d’exploitation. « Managed/serverless » réduit souvent l’ops, mais pas toujours le coût unitaire.
Réflexe d’examen : relever le qualificatif principal, les contraintes absolues (RTO, protocole, chiffrement, ordre, cohérence), puis éliminer les réponses qui violent une propriété native AWS.

IAM, sécurité & gouvernance

IAM Least privilege : une policy JSON combine Effect, Principal, Action, Resource, Condition. Préférer les rôles temporaires à des clés longues et limiter chaque identité à son besoin réel.
IAM Identity Center Fédération SSO centralisée vers plusieurs comptes ; connecter un IdP SAML 2.0/OIDC et éviter les utilisateurs IAM locaux dupliqués.
Organizations / SCP Une SCP ne donne jamais un droit : elle définit le plafond applicable à un compte/OU. Un explicit deny dans IAM, SCP ou permission boundary gagne toujours.
KMS Chiffrement d’enveloppe : une data key chiffre les données, la CMK chiffre la data key. La key policy doit autoriser explicitement les comptes/rôles externes.
CloudTrail Journaliser les appels API (management/data events selon le besoin), centraliser les logs dans S3 et protéger l’historique contre l’altération.
GuardDuty Détection managée de menaces via CloudTrail, VPC Flow Logs et DNS ; Inspector recherche les vulnérabilités EC2/ECR ; Security Hub agrège les findings.
Hiérarchie de décision : refus implicite par défaut → allow explicite requis → tout explicit deny annule l’allow. IAM décide qui ; SCP/permission boundary limitent jusqu’où.

IAM avancé : les couches d’autorisation

Identity policy attachée à un user/group/role ; accorde un droit si l’action, la ressource et les conditions correspondent.
Resource policy attachée à S3, SQS, SNS, KMS ou Lambda ; utile pour l’accès cross-account, avec un Principal explicite.
Permission boundary plafond d’un principal IAM ; elle ne donne aucune autorisation par elle-même. Session policy réduit encore les permissions d’une session STS.
STS AssumeRole fournit des credentials temporaires ; vérifier trust policy du rôle, identity policy de l’appelant, durée et conditions ExternalId/MFA.
Access Analyzer détecte les accès externes involontaires et peut générer une policy à partir de l’activité CloudTrail. Secrets Manager fait tourner les secrets ; Parameter Store convient aux paramètres et secrets simples.
Piège IAM : une SCP, une permission boundary ou une key policy n’accorde pas automatiquement un droit. L’autorisation effective est l’intersection des couches applicables, avec priorité à l’explicit deny.

Sécurité avancée des workloads

AWS WAF règles L7 contre SQLi/XSS, rate-based rules et managed rule groups sur CloudFront, ALB ou API Gateway. Shield protège contre DDoS ; Shield Advanced ajoute visibilité et protections avancées.
Network Firewall inspection stateful/stateless au niveau VPC, souvent centralisée dans une inspection VPC via TGW. Prévoir routes aller/retour et symétrie.
Macie découvre et classe les données sensibles/PII dans S3 ; Detective analyse les relations et la cause d’un finding ; Security Hub agrège les contrôles et findings.
ACM certificats TLS publics renouvelés automatiquement ; certificats privés via Private CA. Pour CloudFront, le certificat doit être dans us-east-1.
S3 hardening Block Public Access, bucket policy minimale, Object Ownership Bucket owner enforced, versioning, Object Lock et VPC endpoint policy selon le besoin.
Responsabilités : AWS sécurise le cloud (infrastructure) ; le client sécurise ce qu’il met dans le cloud (identités, données, configuration, patchs selon le service).

VPC Core & connectivité

VPC Régionnel et isolé : subnets associés à une AZ, route tables et CIDR non chevauchants. Public signifie route vers Internet Gateway, pas seulement une IP publique.
Security Group Au niveau ENI, stateful, uniquement Allow : le retour d’une connexion autorisée est accepté automatiquement.
NACL Au niveau subnet, stateless, Allow et Deny ; règles évaluées par numéro croissant. Autoriser explicitement les ports éphémères de retour.
Endpoints Gateway Endpoint pour S3/DynamoDB (route table, pas de coût horaire) ; Interface Endpoint/PrivateLink pour la plupart des APIs, ENI privés et coût par AZ/données.
NAT Gateway Sortie Internet depuis privé, déployer par AZ pour résilience. Internet Gateway sert au public ; NAT Gateway n’autorise pas les connexions entrantes.
Peering / TGW Peering est direct, privé et non transitif ; Transit Gateway devient le routeur régional hub-and-spoke pour de nombreux VPC et VPN.
Direct Connect Liaison dédiée et stable, mais pas chiffrée par défaut : ajouter VPN/IPsec si le chiffrement est requis. Public VIF pour services publics, private VIF pour VPC, transit VIF vers DXGW/TGW.
Piège Examen : un Security Group ne peut pas refuser une IP ; utiliser un NACL, AWS WAF ou une policy adaptée. Un VPC endpoint évite NAT/Internet uniquement pour les services qu’il dessert.

S3, EBS & systèmes de fichiers

S3 Objet durable, multi-AZ par conception, clé unique par bucket. Versioning protège des suppressions ; Object Lock/WORM impose rétention et legal hold ; SSE-S3 par défaut, SSE-KMS pour contrôle/audit de clés.
S3 classes Standard (actif), Intelligent-Tiering (accès imprévisible), Standard-IA/One Zone-IA (moins fréquent), Glacier Instant/Flexible/Deep Archive (archives). Lifecycle automatise transitions et expiration.
S3 performance Multipart upload pour objets volumineux, presigned URL pour accès temporaire, Transfer Acceleration pour longue distance, CloudFront pour cache global. S3 fournit une forte cohérence read-after-write sur les opérations d’objets ; gérer tout de même retries, erreurs et conflits de réplication.
EBS Bloc attaché à une AZ : gp3 (SSD général, IOPS/throughput séparables), io2 Block Express (IOPS et durabilité critiques), st1 (throughput séquentiel), sc1 (cold). Snapshots incrémentaux S3, chiffrables KMS.
EFS NFS élastique partagé, multi-AZ et adapté à plusieurs EC2/Lambda ; EFS IA réduit le coût des fichiers peu consultés.
FSx Windows File Server pour SMB/AD, Lustre pour HPC/ML et throughput élevé, NetApp ONTAP pour fonctions enterprise, OpenZFS pour workloads ZFS.
Repères : EBS = bloc et une AZ ; EFS = fichiers POSIX partagé ; S3 = objets et API HTTP ; FSx = protocole/plateforme spécialisée. Ne pas monter un volume EBS normal simultanément sur plusieurs AZ.

EC2, Auto Scaling & serverless

EC2 Choisir une famille selon CPU, mémoire, réseau, stockage local ou accélérateur. User data automatise le bootstrap ; AMI et Launch Template rendent le déploiement reproductible.
On-Demand Flexibilité sans engagement ; Reserved/Savings Plans remise contre engagement ; Spot capacité interruptible avec risque de récupération : batch, workers et workloads tolérants.
ASG (Auto Scaling Group) un groupe d’instances décrit par un Launch Template avec une capacité min / desired / max, répartie sur plusieurs AZ pour éliminer le SPOF. Un health check (EC2 ou ELB) déclenche le remplacement automatique des instances « unhealthy » ; l’ASG s’attache à un ELB qui route le trafic vers les instances passées en service.
Politiques de scaling target tracking maintient une métrique (ex. CPU utilisé 60 %) ; step scaling réagit par paliers ; scheduled prévoit une charge connue ; predictive anticipe des patterns historiques. Cooldown/warm-up et termination policies stabilisent ; découpler avec SQS pour absorber les pics.
Élément ASGRôle clé

min / desired / maxBornent la capacité ; desired est la cible initiale, ignorée si elle sort des bornes.

Placement Groups contrôlent la disposition physique des instances sur le matériel AWS : Cluster = instances regroupées sur le même rack dans une seule AZ pour une latence ultra-basse et un throughput élevé ; Spread = instances sur du matériel totalement distinct pour une isolation maximale des pannes, mais avec une limite stricte de 7 instances par AZ ; Partition = instances réparties sur des segments logiques à racks indépendants (jusqu’à 7 partitions par AZ) pour combiner grand scale et tolérance aux pannes matérielles.

ELB ALB = L7 HTTP/S, host/path routing, WAF et TLS ; NLB = L4 TCP/UDP/TLS, très haute performance et IP statique ; GWLB = insertion d’appliances réseau.
Lambda événementiel, pay-per-invocation/durée, stateless ; limites clés à surveiller : durée maximale d’une invocation 15 min, concurrence et taille du package. Pour longue durée/contrôle réseau, ECS/Fargate ou EC2.
Containers ECS est l’orchestrateur AWS intégré ; EKS est Kubernetes managé ; Fargate supprime la gestion des nœuds. ECR stocke les images, déploiement blue/green ou canary via CodeDeploy.
Piège Examen : « scale to zero, stateless, trafic irrégulier » pointe vers Lambda/API Gateway ou Fargate/serverless. Une instance Spot n’est jamais le seul composant d’une base ou d’un service critique sans reprise.

Bases de données & caches

RDS Multi-AZ haute disponibilité avec réplica standby synchrone et failover ; le standby n’est pas une cible de lecture. Read Replicas servent à scaler les lectures et peuvent être promues.
Aurora stockage distribué répliqué sur 3 AZ/6 copies, séparation compute/storage, réplicas Aurora et endpoints reader/writer. Aurora Global Database vise lecture distante et DR cross-Region.
DynamoDB NoSQL clé-valeur/document, accès par partition key ; GSI/LSI pour patterns de requêtes, on-demand ou provisioned capacity, DAX pour cache en mémoire, Global Tables pour multi-région.
ElastiCache Redis pour structures riches, réplication/failover et sessions ; Memcached pour cache simple horizontal. MemoryDB fournit un datastore Redis durable.
Redshift data warehouse analytique ; OpenSearch recherche/logs ; Neptune graph ; DocumentDB document compatible MongoDB ; Timestream séries temporelles.
Choix rapide : transactions relationnelles = RDS/Aurora ; clé-valeur à très grande échelle = DynamoDB ; recherche texte/logs = OpenSearch ; analytique colonne = Redshift ; cache = ElastiCache.

Route 53, CloudFront & observabilité

Route 53 alias vers AWS (pas de coût de query alias), health checks et politiques Simple, Weighted, Latency, Failover, Geolocation/Geoproximity. Private Hosted Zone pour résolution dans VPC.
CloudFront CDN global : cache edge, TLS ACM (certificat dans us-east-1 pour distribution), signed URL/cookie, Origin Access Control vers S3, WAF/Shield.
CloudWatch métriques, logs, alarms, dashboards, Synthetics et Application Signals. Logs Insights analyse les logs ; EventBridge/alarms automatisent une réponse.
X-Ray traces distribuées pour localiser latence et erreurs entre API, Lambda et services. CloudTrail = audit API ; Flow Logs = métadonnées réseau ; CloudWatch = fonctionnement.
Piège Examen : CloudFront est une couche cache/edge, pas un remplacement de Route 53. Route 53 health check + failover DNS ne garantit pas que les clients ignorent instantanément le TTL.

FinOps & Well-Architected

Cost Explorer/Budgets analyser, prévoir et alerter ; un budget alerte mais ne bloque pas automatiquement l’utilisation.
Tags Cost Allocation Tags et comptes séparés rendent l’imputabilité possible. Enlever ressources orphelines, EBS snapshots anciens, Elastic IP inutilisées et NAT excessifs.
Compute Savings Plans/Reserved Instances pour charge stable ; Spot pour interruptible ; Graviton si compatible ; serverless lorsque charge variable et faible exploitation.
Storage/network Lifecycle S3, Intelligent-Tiering, compression, CloudFront, VPC endpoints S3/DynamoDB et réduction des transferts cross-AZ/cross-Region.
Méthode SAA : identifier le qualificatif (« moins cher », « sans opérations », « HA », « latence »), extraire contraintes, éliminer les distracteurs invalides, choisir le service managé qui satisfait exactement le besoin.

SAP-C02 : axes de décision

Complexité organisationnelle — 26% réduire le blast radius, déléguer proprement, isoler les workloads et appliquer une gouvernance centralisée.
Nouvelles solutions — 29% concevoir une architecture complète à partir des contraintes de sécurité, réseau, données, résilience, performance et coût.
Amélioration — 25% diagnostiquer une architecture existante, supprimer la dette opérationnelle, augmenter la résilience et optimiser le coût sans régression.
Migration — 20% choisir le bon 7R, réduire le downtime, traiter les dépendances et automatiser cutover, validation et rollback.
Réflexe SAP : plusieurs réponses peuvent être techniquement possibles. Retenir celle qui respecte toutes les contraintes, minimise l’effort opérationnel et limite le domaine d’impact d’une erreur.

Landing zone & multi-comptes

Organizations Root → OUs → comptes. Séparer management, log archive, security tooling, network/shared services, workloads dev/test/prod pour réduire le blast radius et clarifier la facturation.
Control Tower Automatise la landing zone, Account Factory et guardrails. Preventive guardrails = SCP ; detective guardrails = AWS Config. Une SCP bloque mais n’accorde jamais un droit IAM.
IAM Identity Center SSO centralisé vers les comptes et permission sets. Pour machine-to-machine, utiliser STS AssumeRole et des credentials temporaires, jamais une access key partagée.
Audit central Organization CloudTrail vers un compte log archive S3 avec bucket policy restrictive, Object Lock et séparation des rôles. Config Aggregator consolide la conformité ; GuardDuty admin agrège les findings.
FinOps AWS Budgets, Cost Categories/Allocation Tags et Billing Conductor pour visibilité et showback/chargeback entre business units.
SAP Gotcha : ne pas placer toutes les workloads dans un compte unique « pour simplifier ». Le multi-compte isole les permissions, quotas, logs, facturation et pannes ; une SCP mal appliquée peut toutefois casser les opérations d’un OU entier.

Landing zone : composants clés

Management account conserver le minimum d’actions, activer MFA, ne pas y héberger de workload et protéger l’accès root.
Log Archive S3 central pour CloudTrail, Config et logs réseau ; bucket policy restrictive, Object Lock, versioning et accès d’écriture uniquement pour les services.
Security Tooling delegated administrators pour GuardDuty, Security Hub, Inspector, Macie et IAM Access Analyzer ; centraliser findings et automatiser leur traitement.
Network / Shared Services TGW, DNS Resolver, endpoints, inspection, Active Directory, CI/CD et services partagés dans des comptes dédiés.
StackSets / Service Catalog déployer des contrôles et ressources standardisés dans les OUs ; séparer les templates de plateforme des templates applicatifs.
SAP Gotcha : un guardrail préventif empêche l’action via SCP ; un guardrail détectif constate une dérive via Config. Un contrôle détectif ne bloque pas la création initiale.

Transit Gateway, DX & Cloud WAN

TGW Hub régional pour VPC attachments, VPN et Direct Connect. Utiliser plusieurs route tables TGW (prod/shared/inspection) pour segmentation ; propagation et associations sont distinctes.
RAM partager TGW, subnets ou autres ressources avec des comptes/OU sans créer de peering full mesh. Le partage ne contourne ni IAM ni routes.
DX Gateway relie des Direct Connect locations à VPC via transit/private VIF ; annoncer uniquement les préfixes nécessaires et respecter les limites BGP (la source cite 100 routes maximum dans ce contexte).
Inspection VPC TGW route table → appliance VPC/GWLB → retour symétrique. Centraliser AWS Network Firewall ou appliance partner sans oublier les routes aller/retour et les AZ.
Cloud WAN réseau global managé par segments et core network policy, utile quand l’entreprise combine régions, VPC, sites et besoins de segmentation à grande échelle.
Pattern : on-prem → DX/VPN → DXGW/TGW → inspection segment → workload VPC. VPN fournit le backup de DX ; deux tunnels terminés sur des AZ différentes apportent la résilience.
SAP Gotcha : DX est privé mais pas chiffré par défaut. Pour IPsec sur DX, combiner une public VIF + VPN public, ou une transit VIF + VPN à IP privée selon le design.

Hybrid DNS & PrivateLink

Route 53 Resolver inbound permet au DNS on-prem de résoudre les zones privées AWS via endpoints ENI. Outbound transmet les requêtes AWS vers les resolvers on-prem avec forwarding rules.
Resolver rules centraliser les règles dans un compte réseau et les partager avec RAM. Attention aux boucles de forwarding, à la résolution conditionnelle et aux security groups des endpoints.
Private Hosted Zone associer à plusieurs VPC (ou architecture centralisée selon le besoin). Une zone publique et privée de même nom ont des réponses différentes selon le point de résolution.
PrivateLink provider → NLB → endpoint service ; consumer → interface endpoint. Accès unidirectionnel au service, sans route réseau globale ni CIDR non chevauchant requis.
Overlapping CIDR éviter Peering/TGW IP routing. PrivateLink résout l’exposition service-to-service ; Private NAT peut traduire des flux bidirectionnels quand une vraie connectivité IP est nécessaire.
SAP Gotcha : PrivateLink n’est pas un transit VPC généraliste et ne fournit pas une résolution DNS « magique ». Publier le nom privé, configurer endpoint DNS et autoriser le SG/NLB.

Réseau entreprise : routage & inspection

TGW route tables séparer les associations et propagations : prod peut atteindre shared-services, mais pas nécessairement dev ; documenter les routes effectives et les blackholes.
Central egress private subnets → TGW → egress VPC → NAT Gateway/Network Firewall → IGW. Déployer NAT et endpoints dans plusieurs AZ et contrôler le retour.
Inspection GWLB ou AWS Network Firewall pour filtrage east-west/north-south. La symétrie de routage est indispensable pour une appliance stateful.
DX + VPN Direct Connect fournit le chemin primaire ; VPN Site-to-Site redondant fournit le backup. Deux tunnels et deux points de terminaison évitent un SPOF.
Cloud WAN privilégier pour une politique réseau globale par segments ; TGW reste le choix régional classique pour connecter VPC, VPN et DX.
SAP Gotcha : une route annoncée dans TGW ne garantit pas le chemin retour. Vérifier les tables de routes VPC, TGW, appliance, DX/VPN et les filtres BGP dans les deux directions.

KMS, conformité & cross-account

KMS key policy dans un compte sécurité : autoriser l’utilisation par le compte consommateur, puis la policy IAM du rôle consommateur doit aussi permettre l’action. Les deux portes sont nécessaires.
Multi-Region keys clés répliquées avec même key material/logical key ID pour déchiffrer localement des données répliquées ; elles ne remplacent pas la stratégie de réplication ni les contrôles d’accès.
S3 replication SRR/CRR, versioning sur les deux buckets, IAM role de réplication, KMS grants/key policy cross-account et ownership/ACL adaptés. Re-encryption KMS nécessaire lors d’un changement de clé.
SCP vs key policy une SCP peut bloquer l’appel KMS même si key policy et IAM autorisent ; la policy KMS ne peut pas outrepasser une SCP.
Compliance Config conformance packs, Security Hub standards, Macie pour PII S3, Audit Manager pour preuves et CloudTrail Lake pour analyse des événements.
SAP Gotcha : cocher « encryption enabled » ne suffit pas. Vérifier région de la clé, grants, key policy, rôle de réplication, destination cross-account et capacité à restaurer.

Résilience opérationnelle

Elastic Disaster Recovery réplication continue de serveurs vers une staging area et lancement de l’infrastructure de reprise à la demande ; utile pour rehost DR avec RTO réduit.
Resilience Hub évalue les objectifs de résilience d’une application, identifie les écarts et propose des recommandations ; il ne remplace pas les tests de failover.
AWS Backup Vault Lock impose une rétention immuable en mode compliance ; combiner copies cross-account/cross-Region et politiques Organizations.
FIS Fault Injection Service teste volontairement des défaillances ; limiter l’expérimentation par IAM, tags, stop conditions et fenêtres approuvées.
Runbook inclure quotas, IAM, secrets, certificats ACM, DNS/TTL, réplication, dépendances tierces, observabilité, validation métier et procédure de retour arrière.
SAP Gotcha : une architecture multi-AZ ne suffit pas si le déploiement, les quotas régionaux, les secrets ou les permissions de restauration restent dans une seule région.

Migration : factory & cutover

Discover Migration Hub, Application Discovery Service et Migration Evaluator inventorient dépendances, utilisation, coûts et vagues de migration.
Factory landing zone, comptes, réseau, IAM, logging et templates IaC prêts avant la première vague. Standardiser AMI, tags, backup, monitoring et rollback.
Data full load → CDC → validation des compteurs/checksums → gel court → cutover → observation. Mesurer lag DMS, erreurs applicatives et capacité cible.
Files DataSync pour transferts récurrents et vérifiés ; Storage Gateway pour accès hybride ; Snowball/Snowcone quand la bande passante rend le transfert réseau trop long.
Modernize strangler pattern, façade API, anti-corruption layer, événements de domaine et feature flags permettent de remplacer progressivement sans big bang.
SAP Gotcha : réduire le downtime ne signifie pas supprimer la validation. Une migration sans mesure de CDC lag, tests de cohérence et plan de rollback n’est pas maîtrisée.

Architecture event-driven & API

EventBridge bus central et règles par événement pour découpler domaines. Archive/replay et schema registry aident la gouvernance des contrats.
SQS buffer de back-pressure avec visibilité, retry et DLQ. Garantir idempotence car Standard est at-least-once ; FIFO seulement si ordre/déduplication nécessaires.
SNS fan-out vers plusieurs consommateurs ; combiner SNS→SQS pour isoler les vitesses de traitement. Step Functions gère workflow et compensation.
ECS/EKS/Fargate choisir ECS pour simplicité AWS, EKS pour exigences Kubernetes/portabilité ; Fargate réduit les opérations mais n’est pas toujours le meilleur coût pour capacité stable.
Pattern de migration : API facade → strangler routing → nouveau service → EventBridge/SQS → réplication/CDC → observabilité. Déployer blue/green, canary et feature flags pour limiter le risque.
SAP Gotcha : un bus d’événements n’est pas une file de travail. Utiliser EventBridge pour router, SQS pour retenir jusqu’à consommation et Step Functions pour orchestrer plusieurs étapes.

Améliorer une solution existante

Well-Architected analyser Operational Excellence, Security, Reliability, Performance Efficiency, Cost Optimization et Sustainability ; utiliser AWS Trusted Advisor et les métriques réelles avant de changer.
Observability centraliser CloudWatch cross-account, X-Ray, CloudTrail organization trail, Config Aggregator et Security Hub. Corréler logs, traces, métriques et événements de déploiement.
Performance cache CloudFront/ElastiCache, read replicas, DynamoDB partition design, async queues, compression et placement régional ; ne pas scaler verticalement par réflexe.
Cost rightsizing, Graviton, Savings Plans, Spot, S3 Lifecycle, endpoints, réduction du trafic cross-AZ et extinction des environnements non production.
Operations IaC CloudFormation/CDK/Terraform, pipelines CI/CD, immutable AMI, Systems Manager Patch Manager/Automation et runbooks testés plutôt que scripts manuels.
Posture SAP : plusieurs réponses peuvent fonctionner ; choisir celle qui satisfait toutes les contraintes avec le moins d’effort opérationnel, le plus petit blast radius et une sécurité explicite.

Data platform & analytics

S3 data lake zones raw/clean/curated, formats colonne Parquet, partitionnement et lifecycle ; gouverner l’accès par Lake Formation plutôt que par des buckets publics.
Glue Data Catalog, crawlers et ETL serverless ; Athena SQL sans cluster sur S3 ; contrôler le coût en limitant les scans par partitions et formats compressés.
Redshift warehouse relationnel analytique ; RA3 sépare compute/storage, Spectrum interroge S3. EMR convient aux frameworks big data nécessitant davantage de contrôle.
Kinesis / MSK Kinesis est AWS-native et serverless pour streaming ; MSK convient à la compatibilité Kafka et au contrôle de l’écosystème Kafka.
OpenSearch recherche, logs et agrégations quasi temps réel ; QuickSight visualisation BI. Séparer stockage durable, traitement et index de recherche.
SAP Gotcha : S3 est le stockage du data lake, pas le moteur de requête. Athena/Glue/Lake Formation apportent respectivement requête, catalogue/ETL et gouvernance.

Cas d’entreprise — décisions à haute valeur

Banque mondiale : séparation réglementaire et reprise

Contraintes

  • Comptes prod séparés par région/régulateur, journaux immuables et accès opérateur fédéré.
  • RPO de quelques minutes et RTO inférieur à 30 minutes pour les bases critiques.

Architecture

Control Tower → OUs réglementaires → Identity Center ; CloudTrail/Config/GuardDuty/Security Hub centralisés ; Aurora Global/DynamoDB Global Tables selon le modèle de données ; Route 53/Global Accelerator pour le failover.
SAP Gotcha : la réplication multi-région n’est pas une garantie de cohérence transactionnelle universelle. Choisir le datastore selon les writes, conflits et exigences ACID.
Groupe industriel : datacenter, CIDR chevauchants et modernisation

Contraintes

  • Plusieurs sites avec CIDR historiques identiques, liaison DX principale et VPN de secours.
  • Exposer progressivement des APIs migrées sans connecter les réseaux entiers.

Architecture

DX/VPN → DXGW/TGW pour les préfixes non conflictuels ; PrivateLink (NLB + endpoint service) pour les services aux CIDR conflictuels ; MGN/DMS/SCT pour migrer ; ECS/Fargate + EventBridge/SQS pour moderniser.
SAP Gotcha : PrivateLink expose un service, il ne résout pas une dépendance qui exige une connectivité IP bidirectionnelle complète. Pour cette dernière, examiner Private NAT et la re-numérotation.
Retail global : trafic variable et coûts

Contraintes

  • Pics saisonniers, catalogue mondial, recherche rapide, données client chiffrées et équipes autonomes.
  • Éviter le sur-provisionnement et isoler les coûts par domaine.

Architecture

CloudFront + WAF en edge → API Gateway/Lambda ou ECS → DynamoDB Global Tables pour accès clé-valeur mondial ; SQS/EventBridge pour commandes ; Cost Allocation Tags/Budgets pour FinOps.
SAP Gotcha : ne pas choisir une base relationnelle uniquement parce que les données sont « importantes ». Le pattern d’accès, les transactions et la cohérence décident du service.
Référence de révision personnelle — vérifiez toujours les limites et fonctionnalités dans la documentation AWS de votre région et de la version d’examen.
